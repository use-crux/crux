LLM testing has converged on a sensible baseline: build a dataset, run your prompts against it, score the outputs with exact matches and LLM judges, fail CI below a threshold. Promptfoo, DeepEval, Braintrust, and friends all do this well. If you have no evals at all, start there today.

But teams that run output evals seriously hit the same wall. A score drops from 0.91 to 0.84. CI fails, correctly. Then the debugging starts, because a score is a symptom, not a cause. Was it the prompt edit? The retriever change? A context block getting dropped? The eval told you *that* the system regressed. It cannot tell you *what* regressed, because it only saw the final text.

There is a second, quieter problem: output evals can pass while the system is broken. If retrieval silently returns nothing and the model answers from its own knowledge, a fluent answer can still score fine. You are testing the model's ability to compensate for your harness. Not your harness.

The fix for both is the same: test what the harness *did*, not only what the model *said*.

## What does harness behavior look like as a test subject?

Every model turn is preceded by decisions your code made. Which contexts were included. Which were dropped for budget. What memory was recalled. Whether cached evidence passed freshness. Which model the router picked.

Each of those is deterministic given the same inputs and policies. That makes each of them a legitimate test subject, unlike model output, which you can only test statistically.

Here is what asserting them looks like with Crux's quality system:

```ts title="evals/support.eval.ts"
import { evaluate, target } from '@use-crux/core/quality'
import { supportPrompt } from '../prompts/support'

export default evaluate('support.harness-contract', {
  covers: ['prompt:support'],
  task: target.prompt(supportPrompt, { generate, model }),
  data: [
    { name: 'billing question', input: { question: 'Why was I charged twice?', tier: 'free' } },
    { name: 'enterprise escalation', input: { question: 'SSO is broken', tier: 'enterprise' } },
  ],
  expect: (ctx) => {
    // The customer-profile context must reach the model
    ctx.expect.decisionReport.context.toHaveDisposition(
      'context:customerProfile', 'active',
      { reasonCode: 'context.active' },
    )
    // Enterprise traffic must route to the deep model
    if (ctx.input.tier === 'enterprise') {
      ctx.expect.decisionReport.routing.toHaveOutcome(
        'route:deep', 'selected',
        { reasonCode: 'routing.router.selected' },
      )
    }
  },
})
```

Read the assertions as a contract: for these inputs, the harness assembles the turn this way. When a refactor changes a `when` predicate, or a new high-priority context evicts the profile block under budget, this fails in CI naming the exact decision that changed.

One rule: assert stable machine fields (definition ids, dispositions, reason codes), never display strings. Readouts are copy, and copy changes.

## What should I assert first?

Not everything. Harness contracts earn their keep on the decisions with incident potential. A practical starting set:

- **Presence of the load-bearing context.** The safety policy, the pricing source, the user's plan. Whatever would embarrass you if it silently vanished under budget pressure.
- **Routing promises.** Any "tier X always gets model Y" commitment you have made to customers or to your own margin math.
- **Freshness on decision-relevant evidence.** Assert stale rejections on sources where an outdated answer is worse than no answer.
- **Safety outcomes on known-bad inputs.** Your incident regression cases: this input gets blocked, that one gets redacted.

Four or five assertions covering those categories catch more production regressions than fifty output scores, because they fail at the cause.

## Where do output evals fit?

Harness assertions complement output evals; they don't replace them. The layers adopt incrementally:

1. **Colocated smoke tests.** Data-only cases on the prompt definition (`tests: [...]`). Output-schema validation for free.
2. **An eval file.** `evaluate({ task, data, expect })` with output checks.
3. **Harness assertions.** The decision-report expectations above. Score drops become named causes.
4. **Scorers and gates.** Judges for the fuzzy qualities, with pass-rate thresholds. Failing on any single case gives you flaky builds; thresholds don't.
5. **Baselines.** Promote a good run; every later run auto-compares. "Did my change make things worse?" becomes a diff instead of a feeling.

Each level adds keys to the same object. Nothing gets rewritten.

On level 4, one practice worth adopting early: **audit your judges.** An LLM judge is a model call with all the failure modes that implies. Crux records human pass/fail labels against judge verdicts and reports agreement, a confusion matrix, and Cohen's kappa per judge, so "the judge says quality dropped" is itself a claim with evidence. A judge you have never disagreed with is a judge nobody has checked.

## Isn't LLM CI slow, expensive, and flaky?

Yes, if every run calls the model. The answer is the same one software engineering always gives: record and replay.

```ts
export default evaluate('support.harness-contract', {
  // ...same as above
  replay: 'cassette',
})
```

A cassette records the normalized model calls from a real run. Replay serves them back deterministically. CI spends zero tokens and runs in seconds.

Replay also makes harness assertions exactly reproducible. Same inputs, same recorded model behavior, so any change in the decision report was caused by your code change. That is a real regression test, not a coin flip with a rubric.

Cassette identity is fingerprinted on prompt, model, settings, and schemas, so a stale recording is missed rather than silently reused. Re-record when you intend behavior to change.

## What does this look like day to day?

```bash
crux quality run --ci               # the full contract; gates drive exit codes
crux quality run --failed latest    # rerun only what broke
crux quality diff <run-a> <run-b>   # what actually changed between runs
crux quality promote <experiment>   # mark the new baseline after review
```

Exit code 0 means every declared expectation about your harness still holds. Exit code 1 names the case, the decision, and the reason code. Failing cells carry a failure artifact with the dataset row, cassette id, and repro command, so the fix loop starts at the cause.

The suite also embeds in an existing test runner. The Vitest bridge is one line:

```ts
import supportEval from '../evals/support.eval'

it('support quality', async () => {
  const experiment = await supportEval.run()
  expect(experiment.passed).toBe(true)
})
```

And for building the dataset in the first place, skip the blank page and import real traffic:

```bash
crux quality import-traces --definition support --with-expected
```

Imported rows keep their trace provenance, so when a case regresses you can walk back to the production turn it came from.

## Status and takeaway

Crux is alpha and its quality system is beta. The stability contract for authoring surfaces and record schemas is documented explicitly, and the harness-decision matcher library is still growing.

The shift itself doesn't wait for any particular tool. Stop treating your eval suite as a model-quality dashboard. Treat it as a test suite for the half of the system you control.
