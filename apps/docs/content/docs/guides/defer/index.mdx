---
title: Request-scoped defer()
description: Defer work until the active host completion boundary, or stage durable named Runtime work after durable acceptance.
---

`defer()` registers work that must not stay on the response-critical path. It is
an **invocation-lifetime** primitive, not a domain effect receipt API and not an
alias for `flow.defer()`.

```ts
import { defer } from '@use-crux/core'
```

## Two overloads

### Inline callback

```ts
defer(() => {
  // Starts after the host's declared completion boundary.
  // Does not delay the handler result.
})
```

- Returns `void` (never a thenable)
- Lazy: the callback is not invoked at registration time
- Requires an active host lifetime capability
- Does **not** require the Crux Runtime Engine
- Reliability is bounded by the host (process-local, no automatic crash recovery)

### Named durable target

```ts
import { durableTask } from '@use-crux/core/runtime'

const sendEmail = durableTask('send-email', {
  run: async (input: { messageId: string }) => {
    /* ... */
  },
})

const ref = await defer(sendEmail, { messageId: 'msg_1' })
// ref.kind === 'deferred.work'
// ref.workId, ref.targetId
```

- Returns `Promise<DeferredWorkRef>` after **durable acceptance**, not after
  target execution
- Requires a configured Runtime Engine and a host that can finalize named work
  before committing the response (`durableFinalization: true`)
- Staging failures poison the scope: the host must discard the produced response
  and surface `DEFER_COMMIT_FAILED`

## Completion classes

Hosts declare when inline work may start:

| Class | Meaning | Typical hosts |
| --- | --- | --- |
| `response-finished` | Callbacks start after the response stream is flushed or the framework post-response hook fires | Node HTTP `finish`, Next.js `after()` |
| `handler-returned` | Callbacks start after the handler returns its response object and **may overlap** body streaming | Vercel / Cloudflare `waitUntil` |

Crux reports the active class honestly. It does not pretend every host waits for
network delivery to the client.

## Strict named commit

Named registration is all-or-nothing for the host response:

1. `await defer(target, input)` stages an intent and resolves only after durable acceptance
2. The host adapter awaits the scope’s `committed` barrier before sending the response
3. Any staging or finalization failure rejects `committed` as `DEFER_COMMIT_FAILED`
4. Catching the caller promise does **not** restore a successful response

Best-effort post-response work uses the **callback** overload, not named targets.

## At-least-once edge

After a successful durable finalization, released work is delivered through the
Runtime outbox. If the process dies after finalization but before the client
receives the HTTP response (or before outbox confirmation), side effects may run
even though the client never saw success. Exactly-once side effects are **not**
promised. Design targets to be idempotent.

## Cancellation

Cancellation is cooperative. The SDK aborts a child signal and stops waiting for
drain settlement at host limits, but it cannot preempt a callback that ignores
the signal. Diagnostics never claim preemption.

## Replay safety

Public `defer()` is forbidden inside replayable flow bodies and steps. It throws
`DEFER_REPLAY_UNSAFE`. Durable work inside flows uses `flow.defer(target, input)`,
which keeps stable work identity across replay.

## Difference from Effects and `flow.defer()`

| API | Purpose |
| --- | --- |
| `defer(callback)` | Request-scoped, host-lifetime, non-durable cleanup/side work |
| `await defer(target, input)` | Request-scoped staging of durable Runtime work |
| `flow.defer(target, input)` | Replay-safe durable child work inside a flow |
| Effects (future #196) | Domain effects with receipts/rollback — **not** what `defer()` is |

Inline deferred callbacks get independent failure containment. They are not
domain effect receipts and produce no effect receipt object.

## Observability and Catalog

Public `defer()` sites are indexed as `deferred-work` definitions. Runtime emits
`defer.scheduled` and `defer.run` spans with causal `triggered` edges. Devtools
Catalog and Runs show inline vs named lifecycle states. Internal composition
ports stay quiet (no Catalog row, no user Run root).
