---
title: Signals
description: Publish typed occurrences to local callbacks or durable Flow waits.
---

A Signal is an inert typed event definition. Publication stays process-local when only local callbacks participate, and becomes durable when an activated binding requires recovery.

```ts
import { signal } from "@use-crux/core";
import { z } from "zod";

const orderSubmitted = signal({
  id: "order.submitted",
  schema: z.object({
    orderId: z.string(),
    quantity: z.coerce.number().int().positive(),
  }),
});
```

`signal()` performs no I/O, starts no worker, and returns a frozen definition. It accepts any Standard Schema v1-compatible schema; there is no separate Crux schema package.

## Subscribe to future occurrences

```ts
const unsubscribe = orderSubmitted.subscribe((occurrence) => {
  occurrence.signalId; // "order.submitted"
  occurrence.payload.quantity; // number after schema normalization
});

unsubscribe();
unsubscribe(); // safe: unsubscribe is idempotent
```

Subscriptions exist only in the current JavaScript process. They receive no historical replay, and a restart loses them.

## Publish at acceptance

```ts
const receipt = await orderSubmitted.publish({
  orderId: "order_123",
  quantity: "2",
});

receipt.guarantee; // "process-local" or "durable"
receipt.occurrenceId; // stable for this accepted occurrence
receipt.acceptedAt; // Date
```

The Promise resolves when Crux accepts the normalized occurrence. It does **not** wait for listeners or durable consumers to finish. Slow or failing consumers are isolated from one another and cannot reject an accepted publication.

Schema-invalid input and JSON-unsafe normalized output reject before an occurrence is accepted. Dates, class instances, functions, non-finite numbers, and cyclic values are not JSON-safe; normalize them to plain JSON in the schema.

## Retry safely

Use an idempotency key when an external source can retry the same publication:

```ts
const receipt = await orderSubmitted.publish(payload, {
  idempotencyKey: providerEventId,
});
```

For one Signal definition, the same key and canonical normalized payload return the original receipt and deliver no second callback. Reusing the key with different normalized data rejects with `idempotency_conflict`. Receipts and errors never expose the key or payload values.

## Create filter identities

`when()` creates an inert filtered view. Predicates carry deployed code; match views carry canonical recursive partial-equality data:

```ts
const largeOrder = orderSubmitted.when((payload) => payload.quantity >= 10);
const thisOrder = orderSubmitted.when({ orderId: "order_123" });
```

Included scalar fields compare exactly, nested object fields recurse, and included arrays compare as exact arrays. Filtered views intentionally have no `publish()`, `subscribe()`, or chained `when()` methods.

These views are inert identities. Creating one does not activate a consumer or strengthen the publication guarantee.

## Wait durably from a Flow

Declare a static Signal source in the Flow's `signals` map, then pass that same source to `waitFor()`:

```ts
import { config, flow, signal } from "@use-crux/core";
import { node } from "@use-crux/core/runtime";
import { z } from "zod";

config({
  runtime: node({ store: durableRuntimeStore }),
});

const checksChanged = signal({
  id: "ci.checks.changed",
  schema: z.object({ sha: z.string(), status: z.string() }),
});

const release = flow(
  "release",
  { signals: { checksChanged } },
  async (flow) => {
    const occurrence = await flow.waitFor(checksChanged);
    occurrence.signalId; // "ci.checks.changed"
    occurrence.payload.sha; // string
  },
);
```

`durableRuntimeStore` represents a Runtime adapter that has passed the reactive composite conformance suite. The default store created by `node()` is in-memory and process-local; it is useful for development, but it is not production durability and cannot activate a durable Signal wait.

At Flow activation, Crux checks the concrete mechanical capabilities required for durable delivery: Signal record storage, atomic transactions, durable storage/events/waiters/leases, cursor reads, and at-least-once wake delivery. Missing support rejects with `CAPABILITY_MISSING` before Flow work is allocated or the handler starts, and names the smallest configuration remedy.

The Signal store port is an optional adapter capability so existing Runtime adapters remain source-compatible. Omitting it does not imply support: a durable Signal binding fails preflight until the adapter implements the port and passes reactive composite conformance.

Publication atomically commits the occurrence and every required durable delivery. The durable receipt can therefore return before the Flow completes without risking an accepted occurrence that has no delivery. Wake processing is at least once; occurrence and delivery identities remain stable across retries and restart.

Bare and recursive match sources are resolved from persisted identity and canonical match data. Predicate code stays in the deployed Flow target and is never serialized:

```ts
const passed = checksChanged.when({ status: "passed" });

const releasePassed = flow(
  "release passed",
  { signals: { passed } },
  async (flow) => {
    const occurrence = await flow.waitFor(passed);
  },
);
```

The same map may also contain existing local Flow signal schemas. Static Signal sources are accepted only by `waitFor(source)`; they do not become keys for `flow.suspend(name)` or `handle.signal()`.

## Guarantee boundary

`guarantee: "process-local"` means the occurrence and callbacks are not persisted. It does not survive process exit, serverless suspension, deployment, or a different worker receiving the next request.

`guarantee: "durable"` means the occurrence and all currently required durable deliveries committed atomically. Neither guarantee is proof that a listener or consumer completed. Process-local `subscribe()` callbacks always remain outside the durable requirement set.
