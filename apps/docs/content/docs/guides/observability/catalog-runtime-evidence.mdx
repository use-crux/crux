---
title: Catalog runtime evidence
description: How Catalog and Project Index join authored definitions to live Runs via DefinitionRef activity.
---

The Project Index answers *what is authored*. The observability graph answers *what ran*. Catalog joins them without mixing the two planes: runtime evidence is a derived rollup over graph records, never part of the compiler snapshot or cache identity.

## Two planes, one join key

| Plane | Owner | Facts |
| --- | --- | --- |
| Project Index | Compiler / indexer | Definition id, kind, name, source refs, static/semantic relations |
| Observability graph | Runtime + local Go server | Runs, spans, delivery health, costs, outcomes |
| Join | Runtime-emitted `DefinitionRef` | Canonical `id` matching `store.ProjectDefinition.ID` |

A `DefinitionRef` is emitted only when the runtime already holds a real compiled definition handle (required `id` / literal name / map key). Crux never guesses identity from a stack trace. Anonymous or non-literal definitions simply omit the ref.

```ts
interface DefinitionRef {
  id: string
  kind: ProjectDefinitionKind
  role: DefinitionRefRole
  /** Optional repo-relative source — absolute host paths are never emitted. */
  source?: { file: string; line: number; column?: number }
}
```

Roles describe how the definition participated (`resolved-prompt`, `invoked-agent`, `contributed-tool-policy`, `invoked-flow-step`, …). Kind is the full Project Index kind; role is a coarser relationship label used for display and filtering.

The coverage manifest also declares `runtimeIdentity` for definitions that are not top-level execution owners:

- `definition-ref`: the runtime holds the exact authored identity and records it directly.
- `parent-derived`: the index gives a structural child one exact containment parent; Catalog reports that parent's activity and says the child was not independently observed. Contributors without canonical runtime identity remain truthful zero-runtime states rather than selecting an arbitrary owner.
- `quality`: the existing Quality correlation is authoritative.
- `none`: no truthful live identity path exists.

## Catalog Observability section

Open a definition in Catalog / Index. The **Observability** section is classified from the compiler-owned `DEFINITION_KIND_COVERAGE` manifest plus the server rollup `GET /api/observability/definitions/{id}/activity`:

| Treatment | Kind primary (manifest) | What you see (UI copy) |
| --- | --- | --- |
| **Direct activity** | `directly-observed` | Latest status / time / delivery badge when present; **View N runs** when `N > 0`. Zero activity: *No runs have referenced this definition yet.* |
| **Contributor** | `runtime-contributor` or structural child | Canonical contributor/child refs show *Referenced by N runs*. Parent-derived definitions show *Parent ran in N runs; this definition is not independently observed.* No count is inferred from a display name. |
| **Quality-primary** | `quality-owned` (and dual-tagged cases) | *Quality-primary — correlates through the Quality ↔ observability join…*; secondary direct runtime (e.g. live `scoring.judge` for `scorer`) still surfaces when present |
| **No runtime** | `static-only` / fallback | *Static/declarative — never the target or subject of a runtime primitive.* (or *No runtime evidence path is defined for this kind.*) — no fabricated counts, no dead View Runs link |

Zero activity is a real state, not a broken link. **View N runs** appears only when the activity rollup reports `runCount > 0`.

When direct activity exists, Catalog shows the latest run's status, timestamp, and delivery-health badge, and **View N runs** navigates to Runs pre-filtered to that definition id (`definitionId` query on the Runs list / `GET /api/observability/definitions/{definitionId}/runs`). For parent-derived evidence, the same controls are explicitly based on the indexed parent's id and activity.

## Run Detail → Catalog

Run Detail lists every `DefinitionRef` on the run/span. Resolved ids link into Catalog. If the definition was renamed or deleted since the run:

- The row keeps `role`, `kind`, id, and any sanitized `source` captured on the wire
- The link is **not** a dead navigation target — UI marks it **unresolved** with title text: *Not found in the current Project Index — the source definition may have been renamed or deleted.*

Runs whose refs point at a since-deleted definition still appear in the filtered Runs list. The projection stores runtime-emitted identity only; it is never validated against the current index at write time.

## Coverage honesty

Not every Project Index kind is a top-level run subject. Examples of truthful non-coverage:

- Executed flow steps, parallel branches, and recipe steps carry canonical child refs because their parent identity and authored child key are both available at runtime.
- Other structural children inherit evidence from an indexed parent and are labelled *not independently observed*.
- Knowledge-base and tool-policy contributors carry canonical refs on their owner spans. Storage ports and legacy injectable definitions do not expose a provably canonical runtime id, so Catalog uses indexed owner/parent relations instead of guessing from variable or display names.
- Scorers remain Quality-primary; an authored `judge({ id })` also attaches a scorer ref to its live `scoring.judge` span.
- File-loaded skills without a registry composite id do not invent a join key; registry-loaded skills do emit `DefinitionRef`.
- Compositions (`parallel` / `pipeline` / `swarm` / `consensus`) require an authored `id` so runtime and index share `composition.<kind>:<id>`.

For status vocabulary and delivery health on those runs, see [Runs and delivery health](/docs/guides/observability/runs-and-delivery).
