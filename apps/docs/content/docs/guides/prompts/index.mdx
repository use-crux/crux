Prompt strings, input shapes, output schemas, and model settings tend to scatter across call sites and drift apart as an app grows. `prompt()` puts that whole call contract in one typed place: it is the main unit of LLM work in Crux, describing what the model should see, what input the call accepts, what output shape it should return, and which reusable capabilities should be composed in.

The prompt does not call a model by itself. Adapters such as `@use-crux/ai`, `@use-crux/openai`, `@use-crux/google`, and `@use-crux/anthropic` execute the same prompt definition against their SDKs.

```ts twoslash title="support-prompt.ts"
import { context, md, prompt } from "@use-crux/core";
import { z } from "zod";

const brand = context({
  id: "brand",
  system: md`
    ## Voice

    Be concise and helpful.
  `,
});

export const answerSupport = prompt({
  id: "answer-support",
  use: [brand],
  input: z.object({
    question: z.string(),
  }),
  system: md`
    # Role

    You are a product support assistant.
  `,
  prompt: ({ input }) => md`
    ## Question

    ${input.question}
  `,
  settings: { temperature: 0.2 },
});
```

`md` is optional Markdown-oriented text composition. It uses ordinary TypeScript expressions and resolves to plain text; Crux does not parse or render Markdown. Existing strings remain fully supported and keep their exact behavior:

```ts
prompt({
  system: "You are concise.",
  prompt: ({ input }) => input.question,
});
```

## Compose Prompt Text With `md`

Put a multiline value on its own interpolation line when it should inherit that line's indentation. Keep scalar values inline when no continuation indentation is wanted.

```ts
const audience = "support";
const evidence = md`
  1. Account is active.
  2. Invoice is overdue.
`;

const instructions = md`
  # Review

  - Evidence:
    ${evidence}

  Audience: ${audience}
`;
```

The block interpolation above renders as:

```md
# Review

- Evidence:
  1. Account is active.
  2. Invoice is overdue.

Audience: support
```

Use TypeScript for conditions and repetition. `false`, `null`, and `undefined` omit content; when one is alone on a block line, its carrier line disappears without leaving an extra blank line. Arrays of fragments render one item per line in block position.

```ts
const warning = input.warning && md`> Warning: ${input.warning}`;

const report = md`
  # Report

  ${warning}

  ## Events

  ${input.events.map((event) => md`- **${event.type}:** ${event.summary}`)}
`;
```

Objects are rejected as ordinary interpolations so they cannot silently become `[object Object]`. Make intentional JSON explicit:

````ts
const account = md`
  ## Account

  ```json
  ${md.json(input.account)}
  ```
`;
````

Extract a named fragment when nesting starts to obscure the prompt:

```ts
const outputRules = md`
  ## Output

  - State uncertainty.
  - Cite the relevant event.
`;

const supportSystem = md`
  # Role

  You are a support specialist.

  ${outputRules}
`;
```

Structured text does not change capability placement. Contexts, memory, retrieval, skills, and other contributors still belong in `use: []`; a context's `md` value only formats that context's own contribution.

Crux-aware developer tools can recognize canonical `md` tags through supported
imports, aliases, and re-exports. The Project Index records source authoring
evidence as `metadata.promptText` with `tag: "md"`, `language: "markdown"`, and
a `static` or `dynamic` lifecycle; this does not render Markdown or mark text
trusted. If `tsconfig.paths` can intercept the exact `@use-crux/core` package
root, source attribution fails closed, while runtime prompt behavior remains
unchanged. See the [prompt
reference](/docs/reference/crux-core/prompts#inspection-and-project-index-evidence)
for the exact shape.

## The Mental Model

A prompt owns the call contract.

```ts
prompt({
  id: "answer-support",
  use: [brand, docs, memory],
  input: InputSchema,
  output: OutputSchema,
  system: "Who the assistant is.",
  prompt: ({ input }) => `What the user asked: ${input.question}`,
});
```

Think of the fields this way:

| Field      | What it owns                                                                                                                                                                                                                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`       | Stable identity for logs, evals, cache keys, and devtools                                                                                                                                                                                                                                                                                          |
| `input`    | Runtime data this prompt accepts                                                                                                                                                                                                                                                                                                                   |
| `output`   | Structured output schema. Omit it for plain text generation.                                                                                                                                                                                                                                                                                       |
| `system`   | The prompt's role, policy, and high-level instructions                                                                                                                                                                                                                                                                                             |
| `prompt`   | The user/task message for single-turn calls                                                                                                                                                                                                                                                                                                        |
| `messages` | Full message history for chat or few-shot calls                                                                                                                                                                                                                                                                                                    |
| `use`      | Reusable capabilities: [contexts](/docs/guides/contexts), [memory](/docs/guides/memory), [retrieval](/docs/guides/retrieval), [grounding](/docs/guides/retrieval/grounding), [blackboards](/docs/guides/agents/blackboard), [skills](/docs/guides/skills), and [custom contributors](/docs/reference/crux-core/prompts#custom-contributor-entries) |
| `tools`    | Prompt-local tools for this call                                                                                                                                                                                                                                                                                                                   |
| `settings` | Default generation settings such as temperature and max tokens                                                                                                                                                                                                                                                                                     |
| `tests`    | Inline eval cases for CI and local regression checks                                                                                                                                                                                                                                                                                               |

The normal path is composition through `use`. Manual helpers like `asContext()` and `asTools()` exist for advanced or framework-specific wiring, but users should not need them for ordinary Crux prompts.

Entries in `use` can add instructions, tools, constraints, metadata, or lifecycle behavior during prompt resolution. Custom entries use [`contributor()`](/docs/reference/crux-core/prompts#custom-contributor-entries); dedicated primitives such as [skills](/docs/guides/skills), [memory](/docs/guides/memory), [blackboards](/docs/guides/agents/blackboard), [retrieval](/docs/guides/retrieval), and [grounding](/docs/guides/retrieval/grounding) have first-class APIs.

## Text Output

Omit `output` when the model should return text.

```ts twoslash title="text-prompt.ts"
import { prompt } from "@use-crux/core";
import { z } from "zod";

const rewrite = prompt({
  id: "rewrite",
  input: z.object({
    text: z.string(),
    tone: z.enum(["clear", "friendly", "direct"]),
  }),
  system: "Rewrite text without changing the meaning.",
  prompt: ({ input }) => `Tone: ${input.tone}\n\n${input.text}`,
});
```

```ts title="run.ts"
import { generate } from "@use-crux/ai";
import { openai } from "@ai-sdk/openai";

const result = await generate(rewrite, {
  model: openai("gpt-4o-mini"),
  input: {
    text: "The deployment failed due to credentials.",
    tone: "friendly",
  },
});

result.text;
```

## Structured Output

Add `output` when downstream code needs typed data. Adapters switch to structured generation and validate the result with Zod.

**You write one schema.** Crux compiles a provider-compatible wire schema from it, decodes anything that compilation introduced, and validates the response against the schema you actually authored. You never maintain a second provider-shaped copy, and `result.object` is typed from your Zod type on every provider.

```
your Zod schema ──compile──▶ provider wire schema ──▶ model
                                                       │
your Zod schema ◀──validate── decoded response ◀───────┘
```

Because providers disagree about JSON Schema, the compiler lowers your schema to what the target accepts: inlining references, dropping keywords the provider rejects, and setting `additionalProperties` per its rules. If a provider cannot express structured output at all, the call fails before any network request instead of silently returning text.

```ts twoslash title="structured-prompt.ts"
import { prompt } from "@use-crux/core";
import { z } from "zod";

const classifyTicket = prompt({
  id: "classify-ticket",
  input: z.object({
    subject: z.string(),
    body: z.string(),
  }),
  output: z.object({
    category: z.enum(["billing", "auth", "bug", "other"]),
    urgency: z.enum(["low", "normal", "high"]),
    summary: z.string(),
  }),
  system: "Classify support tickets for routing.",
  prompt: ({ input }) => `${input.subject}\n\n${input.body}`,
});
```

```ts title="run.ts"
const result = await generate(classifyTicket, {
  model,
  input: {
    subject: "SSO stopped working",
    body: "Our Okta login fails after rotating certificates.",
  },
});

result.object.category;
result.object.urgency;
```

### Optional And Nullable Fields

Some providers require every property to be listed as required. Rather than making
you flatten your schema, Crux lowers an **optional-only** field (`.optional()`, not
`.nullable()`) to required-and-nullable on the wire, then deletes the property again
when the model returns `null`:

```ts
output: z.object({
  title: z.string(),
  subtitle: z.string().optional(),
});
```

| You wrote                    | On the wire (strict provider) | Model returns   | You receive         |
| ---------------------------- | ----------------------------- | --------------- | ------------------- |
| `z.string().optional()`      | required, `string \| null`    | `null`          | property absent     |
| `z.string().optional()`      | required, `string \| null`    | `"Hi"`          | `"Hi"`              |
| `z.string().nullable()`      | required, `string \| null`    | `null`          | `null`              |

`.optional()` therefore still means "may be absent", and `.nullable()` still means
"may be null" — the two never collapse into each other. A field that is *both*
optional and nullable is left alone, so an authored `null` is never mistaken for
the transport sentinel.

<Callout type="info">
  This encoding must be reversible, so Crux refuses to apply it where it cannot prove
  a returned `null` came from the encoding rather than from your schema. An optional
  property throws `CruxUnsupportedSchemaError` at compile time — before any request,
  naming the offending path — when it sits inside a recursive schema, a union branch,
  or an intersection/tuple, or when it is literally named `"*"` (which collides with
  the decode manifest's array wildcard). Make the field required, or give it an
  explicit `.nullable()` meaning.
</Callout>

## Compose Capabilities With `use`

`use` is the main Crux composition surface. Put the capability in the array; Crux resolves the right context, tools, constraints, metadata, and lifecycle behavior.

```ts title="composition.ts"
import { prompt, context } from "@use-crux/core";
import { memory, recentMessages, facts } from "@use-crux/core/memory";
import { grounding } from "@use-crux/core/retrieval";
import { skill } from "@use-crux/core/skill/node";

const policy = context({
  id: "support-policy",
  system: "Do not invent product behavior. Ask for clarification when needed.",
});

const userMemory = memory({
  id: "user-memory",
  store,
  namespace: ({ input }) => `user:${input.userId}`,
  blocks: [
    recentMessages({ id: "recent", maxMessages: 8 }),
    facts({ id: "facts", embed: dense }),
  ],
});

const docsGrounding = grounding({
  id: "docs-grounding",
  retriever: docs,
  inject: "both",
  citations: true,
});

const supportTroubleshooting = skill.fromFile(
  "./skills/support-troubleshooting/SKILL.md",
);

const support = prompt({
  id: "support",
  use: [policy, userMemory, docsGrounding, supportTroubleshooting],
  input: z.object({
    userId: z.string(),
    question: z.string(),
  }),
  system: "Answer the support question.",
  prompt: ({ input }) => input.question,
});
```

This is intentionally boring at the call site. The prompt author names the dependencies; each primitive decides what it contributes.

## Put Reusable Wiring In A Context

If several prompts should share the same policy plus the same [retrieval](/docs/guides/retrieval), [memory](/docs/guides/memory), or [skills](/docs/guides/skills), package that as a context.

```ts title="capability-context.ts"
const supportKnowledge = context({
  id: "support-knowledge",
  use: [docsGrounding, userMemory, supportTroubleshooting],
  system:
    "Use product docs first. Use memory only for user-specific details. Load the troubleshooting skill when the question requires diagnostic steps.",
});

const reply = prompt({
  id: "reply",
  use: [supportKnowledge],
  input: z.object({
    userId: z.string(),
    question: z.string(),
  }),
  system: "You are a support assistant.",
  prompt: ({ input }) => input.question,
});
```

Use direct `prompt({ use: [...] })` for one-off wiring. Use `context({ use: [...] })` when you want a reusable product capability.

## System + Prompt vs Messages

Use `system` + `prompt` for the common single-turn shape.

```ts twoslash title="single-turn.ts"
import { prompt } from "@use-crux/core";
import { z } from "zod";

const titleIdeas = prompt({
  id: "title-ideas",
  input: z.object({ topic: z.string() }),
  system: "Generate practical article titles.",
  prompt: ({ input }) => `Topic: ${input.topic}`,
});
```

Use `messages` when you need a full chat transcript, few-shot examples, or role-specific turns.

```ts twoslash title="messages.ts"
import { prompt } from "@use-crux/core";
import { z } from "zod";

const chatReply = prompt({
  id: "chat-reply",
  input: z.object({
    userMessage: z.string(),
  }),
  messages: ({ input }) => [
    { role: "system", content: "Answer as a careful assistant." },
    { role: "user", content: "Answer in one sentence." },
    { role: "assistant", content: "I will keep responses concise." },
    { role: "user", content: input.userMessage },
  ],
});
```

Do not define `system` or `prompt` together with `messages` unless the adapter guide explicitly documents that combination. `messages` is for cases where the message list is the source of truth.

## Inspect Before You Run

Use `.resolve()` or `.inspect()` when debugging composition. This is the fastest way to see what `use` actually injected.

```ts title="inspect.ts"
const resolved = await support.resolve({
  input: {
    userId: "user_123",
    question: "How do I configure SSO?",
  },
  provider: "openai",
  modelId: "gpt-4o",
});

console.log(resolved.system);
console.log(Object.keys(resolved.tools ?? {}));
```

```ts title="budget-debug.ts"
const inspection = await support.inspect({
  input: {
    userId: "user_123",
    question: "How do I configure SSO?",
  },
  tokenBudget: 4000,
});

console.log(inspection.system.parts);
console.log(inspection.droppedContexts);
console.log(inspection.excludedContexts);
```

## What To Reach For

| Need                                       | Use                                                                                                                                                                    |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One model call with typed input/output     | `prompt()`                                                                                                                                                             |
| Reusable instructions or input fields      | [`context()`](/docs/guides/contexts) in `use`                                                                                                                          |
| Runtime conditional instructions           | [`context({ when })`](/docs/guides/contexts), [`when()`](/docs/reference/crux-core/contexts), or [`match()`](/docs/reference/crux-core/contexts)                       |
| Durable user/session recall                | [`memory()`](/docs/guides/memory) in `use`                                                                                                                             |
| Retrieve documents as evidence             | [`retriever()`](/docs/guides/retrieval/querying), [`retrievalRecipe()`](/docs/guides/retrieval/recipes), or [`grounding()`](/docs/guides/retrieval/grounding) in `use` |
| Markdown instruction sets loaded on demand | [`skill()`](/docs/guides/skills) in `use`                                                                                                                              |
| Shared coordination state                  | [`blackboard()`](/docs/guides/agents/blackboard) in `use`                                                                                                              |
| Citation and answer constraints            | [`grounding()`](/docs/guides/retrieval/grounding) or [`constraints`](/docs/guides/safety/constraints)                                                                  |
| CI regression testing                      | `tests` or [`evaluate()`](/docs/guides/evals)                                                                                                                          |
| Provider-specific prompt tweaks            | `adapt`                                                                                                                                                                |

## How This Fits With The Rest Of Crux

- **[Contexts](/docs/guides/contexts)** package reusable system text, inputs, tools, and nested capabilities.
- **[Retrieval](/docs/guides/retrieval)** and **[grounding](/docs/guides/retrieval/grounding)** inject evidence directly or expose search tools on demand.
- **[Memory](/docs/guides/memory)** injects private recall and capture behavior through the same `use` array.
- **[Skills](/docs/guides/skills)** inject a lightweight index plus `LoadSkill` and `LoadReference` tools so the model can pull Markdown instructions on demand.
- **[Blackboards](/docs/guides/agents/blackboard)** inject shared state and focused state-update tools for multi-agent coordination.
- **[Tools](/docs/guides/tools)** can live on prompts, contexts, or injected primitives.
- **[Semantic response cache](/docs/guides/prompts/semantic-cache)** reuses safe prompt results for similar inputs.
- **[Eval](/docs/guides/evals)** runs prompt and RAG regression evaluations in CI and devtools.
