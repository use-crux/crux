---
title: Model Fallback
description: Automatically try backup models when your primary model fails — rate limits, outages, timeouts.
---

When a model provider is down, rate-limited, or timing out, your app should keep working. `fallback()` wraps multiple models into a single reference that tries each in order until one succeeds.

```ts
import { fallback } from '@crux/core'
import { generate } from '@crux/ai'
import { openai } from '@ai-sdk/openai'
import { anthropic } from '@ai-sdk/anthropic'

const result = await generate(myPrompt, {
  model: fallback(openai('gpt-4o'), anthropic('claude-sonnet-4-20250514')),
  input: { query: 'Explain quantum computing' },
})
```

If OpenAI returns a 429 (rate limit) or 500 (server error), Crux automatically retries with Claude. No try/catch needed.

## When do you need this?

- **Production resilience** — your app must stay up even when a provider has an outage
- **Rate limit handling** — high-volume apps that hit provider rate limits
- **Cost optimization** — try a cheaper model first, fall back to a more capable one

If you only use one model provider and are okay with errors propagating, you don't need `fallback()`.

## Error classification

Not all errors trigger fallback. Crux classifies errors into categories:

| Category | Triggers | Examples |
|----------|----------|---------|
| `rate_limit` | HTTP 429 | Provider rate limit exceeded |
| `timeout` | `ETIMEDOUT`, `AbortError` | Model took too long to respond |
| `server_error` | HTTP 500–599 | Provider internal error, bad gateway |
| `connection_error` | `ECONNREFUSED`, `ENOTFOUND`, fetch failures | DNS failure, provider unreachable |
| `auth_error` | HTTP 401, 403 | Invalid API key, insufficient permissions |
| `validation_exhausted` | `ValidationExhaustedError` | All [validation retries](/docs/guides/safety/constraints) exhausted |

**Validation errors (HTTP 400), content policy violations, and unknown errors do NOT trigger fallback** — they are thrown immediately since retrying with a different model won't help. However, `validation_exhausted` errors (from structured output retry) DO trigger fallback — a stronger model may produce valid output.

### Filtering error categories

By default, all classified errors trigger fallback. Use `on` to restrict:

```ts
const model = fallback(primary, backup, {
  on: ['rate_limit', 'timeout'], // only fall back on these
})
```

Server errors and connection errors would be thrown immediately in this configuration.

### Custom error predicates

For edge cases beyond the built-in categories, provide a `shouldFallback` predicate. It takes priority over `on`:

```ts
const model = fallback(gpt4o, claudeSonnet, {
  shouldFallback: (error) => {
    // Fall back on content filter errors (normally HTTP 400 = no fallback)
    if (error.code === 'content_filter') return true
    // Fall back on rate limits
    if (error.status === 429) return true
    return false
  },
})
```

When both `on` and `shouldFallback` are set, the predicate wins.

## Inspecting fallback results

When fallback occurs, the result includes metadata:

```ts
const result = await generate(myPrompt, {
  model: fallback(gpt4o, claudeSonnet),
  input,
})

if (result._meta.fallback) {
  console.log(`Took ${result._meta.fallback.attempts} attempts`)
  console.log(`Failed models: ${result._meta.fallback.failedModels.join(', ')}`)
}
```

The `_meta.fallback` object contains:

| Field | Type | Description |
|-------|------|-------------|
| `attempts` | `number` | Total attempts including the successful one |
| `failedModels` | `string[]` | Model IDs that failed |
| `details` | `FallbackAttemptDetail[]` | Per-attempt breakdown |

Each detail entry has: `model`, `durationMs`, `status` (`'success'` or `'error'`), `error?`, `errorCategory?`, `cost?`.

When the first model succeeds, `_meta.fallback` is `undefined` (no fallback needed).

## All models fail

When every model in the fallback chain fails, Crux throws an `AggregateError` containing all individual errors:

```ts
try {
  await generate(myPrompt, {
    model: fallback(modelA, modelB, modelC),
    input,
  })
} catch (error) {
  if (error instanceof AggregateError) {
    console.log(error.message) // "All 3 fallback models failed"
    error.errors.forEach((e, i) => {
      console.log(`  Model ${i + 1}: ${e.message}`)
    })
  }
}
```

## Observability callbacks

Use `onAttemptError` to log or alert when a model fails:

```ts
const model = fallback(gpt4o, claudeSonnet, {
  id: 'resilient-model',
  onAttemptError: (error, attempt, model) => {
    logger.warn(`Fallback attempt ${attempt} failed`, {
      model: model.modelId,
      error: error.message,
    })
  },
})
```

`id` is optional for execution, but recommended when the fallback policy is part of your authored architecture. The catalog indexes it as `routing.fallback` with ordered `routing.fallback.option` children, and runtime `fallback.attempt` spans include the same `routingId`.

## Devtools

Each fallback attempt appears as a child trace in devtools:

```
crux.generate (fallback)
├── attempt:1 model:gpt-4o        status:error (rate_limit)
└── attempt:2 model:claude-sonnet  status:success
```

## Streaming

`fallback()` works with `stream()` too. Fallback only triggers on start/connection failures — once chunks start flowing, the stream is committed to that model.

```ts
import { stream } from '@crux/ai'

const result = await stream(myPrompt, {
  model: fallback(gpt4o, claudeSonnet),
  input,
})
// If gpt4o fails to connect, retries with claude
// If gpt4o starts streaming then errors mid-stream, the error propagates
```

## Per-attempt timeout

Set `timeout` to abort slow models before trying the next one. Without this, a hanging model blocks all fallbacks.

```ts
const model = fallback(gpt4o, claudeSonnet, {
  timeout: 10_000, // abort after 10 seconds per attempt
})
```

Timed-out attempts are classified as `'timeout'` errors. Works with both `generate()` and `stream()`.

## Interaction with flows

`fallback()` composes naturally with `flow()`. Fallback is model-level (retry different models within a single `generate()` call), while flow retries are step-level (re-run the entire step). They stack:

```ts
const pipeline = flow('pipeline', async (flow) => {
  // If gpt-4o rate-limits, try claude. If both fail, retry the whole step.
  await flow.step('analyze', { retry: 2 }, () =>
    generate(analyzePrompt, {
      model: fallback(gpt4o, claudeSonnet),
      input,
    })
  )
})

await pipeline.run()
```
