## Mental model

`@crux/indexer` is the Project Index compiler. It turns authored source files into definitions, source refs, relations, lint findings, source rows, snapshots, and incremental patches.

Extensions contribute facts through compiler slots:

1. `sources` discover source candidates.
2. `parsers` turn source content into compiler-owned source views.
3. `extractors` emit intermediate definitions, unresolved references, local source refs, and diagnostics.
4. `resolvers` link unresolved references into validated index relations and cross-file source refs.
5. `rules` produce index diagnostics and lint findings over resolved facts.
6. `emitters` produce snapshots, patches, source rows, reports, or other artifacts.

V1 exposes the shape experimentally. Extractors and relation specs are public authoring concepts, and
packages can be loaded from explicit `crux.config.ts` references when the project allowlists them.
Built-in resolver behavior remains compiler-owned. Custom sources, parsers, resolver authoring, custom
third-party rule execution, emitters, queries, and sandboxing are reserved. Call patterns can already
use `importFrom` to avoid matching same-named local helpers from unrelated modules.

Internally, first-party rule identities are included in extension runtime cache inputs. That keeps future query-backed or incremental rule execution compatible with the current manifest shape without exposing custom rule loading yet.

`importFrom` matches the authored module specifier exactly, including tsconfig path aliases after the import itself has been resolved. Package subpaths are not treated as wildcards: list `@crux/core` and `@crux/core/tools` separately if an extractor should support both.

## Extension shape

```ts
import { facts, type IndexerExtension } from '@crux/indexer/extensions'

export const acmeToolsExtension: IndexerExtension = {
  name: '@acme/tools',
  version: '1',
  extractors: [
    {
      name: 'acme.defineTool',
      patterns: [{ kind: 'call', name: 'defineTool', importFrom: ['@acme/tools'] }],
      extract(ctx) {
        if (!ctx.config) return { kind: 'none' }
        const name = ctx.config.string('name') ?? ctx.args.string(0) ?? ctx.source.localName
        const id = `tool:${ctx.source.safeId(name)}`
        const input = ctx.sourceRef.schemaProperty({
          property: 'input',
          definitionId: id,
        })

        return facts({
          definitions: [
            ctx.define.definition({
              variableName: ctx.source.variableName,
              id,
              kind: 'tool',
              name,
              metadata: {
                exportName: ctx.source.variableName,
                description: ctx.config.string('description'),
                inputSchema: ctx.config.schema('input') ?? input.schema,
              },
            }),
          ],
          sourceRefs: [
            ...input.sourceRefs,
            ...[
              ctx.sourceRef.callbackProperty({
                property: 'execute',
                role: 'handler',
                definitionId: id,
              }),
            ].filter(Boolean),
          ],
        })
      },
    },
  ],
}
```

This example shows the intended shape, not a stable public plugin contract.

V1 extracted definitions still normalize into the typed `@crux/core/project-index` definition kinds. Arbitrary third-party definition kinds are reserved for a later index-contract decision.

## Package loading

Publish an extension as an ordinary ESM package that exports a manifest value. Importing that package
is trusted code execution, so Crux only loads packages named in `crux.config.ts` and accepted by the
project trust policy.

```ts
// packages/acme-crux-indexer/src/index.ts
import { facts, type IndexerExtension } from '@crux/indexer/extensions'

export default {
  name: '@acme/crux-indexer',
  version: '1',
  crux: {
    indexer: '^0.1.0',
    projectIndexSchema: 1,
  },
  extractors: [
    {
      name: '@acme/widget',
      patterns: [{ kind: 'call', name: 'defineWidget', importFrom: ['@acme/widgets'] }],
      extract(ctx) {
        const name = ctx.config?.string('id') ?? ctx.source.localName
        const id = `tool:${ctx.source.safeId(name)}`

        return facts({
          definitions: [
            ctx.define.definition({
              variableName: ctx.source.variableName,
              id,
              kind: 'tool',
              name,
              metadata: { extension: '@acme/crux-indexer' },
            }),
          ],
        })
      },
    },
  ],
} satisfies IndexerExtension
```

Then opt into the package from the consuming project:

```ts
// crux.config.ts
import { config, createPrompts } from '@crux/core'

export default config({
  prompts: createPrompts({}),
  indexer: {
    extensions: [{ package: '@acme/crux-indexer', version: '^1.0.0' }],
    trust: {
      mode: 'allowlisted',
      allow: ['@acme/crux-indexer'],
    },
  },
})
```

The loader resolves the package from the project root, reads the installed package version from the
nearest `package.json`, imports the selected export (`default` unless `export` is configured), and
then validates the manifest. `version` in `crux.config.ts` checks the installed package version, not
the manifest's internal behavior version.

Use `trust.mode: 'first-party-only'` as the default. Use `allowlisted` for real third-party packages.
Use `unsafe-local-dev` only for local experimentation because it allows any configured package unless
explicitly denied.

## Relation specs

Extractors can emit unresolved references with `ctx.ref.*`. A relation spec declares the meaning and
allowed endpoints for the relation type before resolver code turns those references into Project Index
relations.

```ts
import type { IndexerExtension } from '@crux/indexer/extensions'

export default {
  name: '@acme/crux-indexer',
  version: '1',
  crux: { indexer: '^0.1.0', projectIndexSchema: 1 },
  relations: [
    {
      type: '@acme/crux-indexer/widget.uses_tool',
      fromKinds: ['tool'],
      toKinds: ['tool'],
      presentation: 'both',
      runtimeJoin: false,
    },
  ],
  extractors: [
    {
      name: '@acme/widget',
      patterns: [{ kind: 'call', name: 'defineWidget', importFrom: ['@acme/widgets'] }],
      extract(ctx) {
        const toolName = ctx.config?.reference('tool')
        return facts({
          references: toolName ? [ctx.ref.variable('@acme/crux-indexer/widget.uses_tool', toolName)] : [],
        })
      },
    },
  ],
} satisfies IndexerExtension
```

Use package-namespaced relation types for third-party extensions. Built-in Crux relation names are
reserved for first-party extractors.

## Rule declarations

The manifest type includes `rules` with docs, message ids, option schema, and analysis-tier metadata.
First-party Crux rules already execute through this slot and expose `ruleDescriptors` to devtools.
Third-party rule execution is still reserved until the public semantic read model, option validation,
and suppression semantics are frozen.

When that slot opens to third-party packages, rule checks should follow the same rule as extractors:
read immutable definitions/relations, optionally read a stable `SemanticReadModel` when declared with
`requires: ['semantic']`, and return lint findings without mutating compiler state.

## Design rules

Extractors return immutable facts. They do not mutate the index graph, cache, registry, diagnostics array, or final snapshot.

Extractors should stay source-local where possible. Cross-file linking belongs to resolver slots so file-local extraction can remain cacheable for incremental indexing.

Relation specs are required before relation refs can become index relations. Unknown relation types are setup errors for first-party internals.

Raw TypeScript nodes are not stable API and are not exposed from the public authoring barrel. First-party extractors may use internal compiler-owned traversal helpers while they are being hardened, but the stable compiler boundary should use Crux-owned source views, match data, import-aware patterns, object readers, and builders.

Stable extractor helpers currently cover the common first-party static extraction path:

- `ctx.args` reads literal factory arguments such as `defineThing('id', { ... })`.
- `ctx.config` reads object-literal configuration, local constants, JSON-safe values, identifiers, arrays, nested objects, object maps, and JSON Schema projections.
- `ctx.config.reference(...)` reads identifier-like references, including shorthand properties and property-access expressions, without exposing native parser nodes.
- `ctx.config.callObject(...)` and `ctx.config.callObjectArray(...)` read configured helper calls, such as stores or memory blocks, without exposing native parser nodes.
- `ctx.source.safeId(...)` sanitizes authored names for index id segments using the same compiler-owned rule as the built-in extractors.
- `ctx.define` and `ctx.ref` build extracted definitions and unresolved references.
- `ctx.sourceRef` builds property, callback, schema, template interpolation, and helper source refs without exposing TypeScript nodes.

## Extractor context

`extract(ctx)` is a pure function from one parser-owned source match to an `ExtractResult`. The context is deliberately made of readers and builders instead of graph handles:

- `ctx.extension` and `ctx.extractor` identify the contribution for diagnostics, registry ordering, and future cache keys.
- `ctx.match` describes the matched call or constructor name without exposing the AST node.
- `ctx.source` provides project root, source file, authored variable name, a deterministic local fallback name, and compiler-compatible id sanitization.
- `ctx.args` reads positional literal arguments. Unsupported expressions return `undefined` or empty arrays.
- `ctx.config` reads the selected object/config argument. Missing configs are `undefined`; extractors should return `none()` or a degraded result instead of throwing.
- `ctx.define.definition(...)` builds index definitions with compiler-owned source defaults. Prefer it over constructing `ProjectDefinition` objects manually.
- `ctx.ref.variable(...)` records an authored identifier/import binding for later resolver binding. `ctx.ref.id(...)` is for already-stable index ids.
- `ctx.sourceRef.*` returns supplemental source refs for properties, callbacks, schemas, template interpolations, and helper functions.

The return value should be data, not side effects:

```ts
return facts({
  definitions: [ctx.define.definition({ variableName, id, kind: 'tool', name })],
  references: [ctx.ref.variable('agent.uses_tool', 'writerTool')],
})
```

Avoid patterns that mutate compiler-owned state:

```ts
// Do not do this.
ctx.graph.addDefinition(definition)
ctx.diagnostics.push(diagnostic)
ctx.cache.set(key, value)
```

Traversal-heavy behavior can still use internal helpers inside first-party extractors. Those helpers are not part of the future third-party contract.

Crux may add internal traversal helpers for first-party extractors that need complex source walks, but traversal is not the stable extension model. Stable extensions should match source shapes, read compiler-owned views, and return facts.

## Incremental indexing

The compiler adds baseline dependencies such as source file content, extension identity, extractor identity, matched imports, and config/compiler boundary hashes. Extractors can declare additional dependencies when they read helper files, imported schema sources, virtual sources, or later semantic inputs.

Those dependencies feed static cache keys and future query-backed compiler execution. If graph evidence is incomplete or unsafe, Crux keeps the existing full reindex fallback.

## Current status

The first implementation routes first-party static extractors and built-in index lint rules through a Crux core extension manifest and exposes `@crux/indexer/extensions` as experimental. Full static discovery and incremental AST partial indexing now parse through fact-backed compiler helpers, run internal rule contributions over resolved facts, and project through compiler result emitters into the existing index result shapes. The stable user-facing index contract remains `@crux/core/project-index` plus `crux dev`, `crux lint`, and the local devtools APIs.

All first-party static primitive call names are registered through the Crux core extension manifest. The removed primitive extractor registry is no longer part of the active extension boundary. Most extractors use stable readers and source-ref builders directly; routing and flow emit facts directly, while their traversal-heavy helpers still consume parser-owned TypeScript structures through compiler-owned internal helpers. They can be hardened behind the same API without changing the extension boundary.
