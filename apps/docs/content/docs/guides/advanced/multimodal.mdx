---
title: Multimodal messages
description: Send images and files through Crux messages while keeping guardrails, memory, cache, and telemetry text-safe.
---

Crux uses one canonical content vocabulary for multimodal chat: `Message.content` is either a string or a readonly `ContentPart[]`. Strings keep existing text-only code working. Parts let prompts, managed adapter calls, headless codecs, tool results, Convex mirrors, observability, and test cassettes describe the same visible content without provider-specific message shapes leaking through your app.

## Author parts

Use builders when you have bytes or URLs at the edge:

```ts
import { filePart, imagePart, prompt, textPart } from "@use-crux/core";
import { generate } from "@use-crux/ai";

const inspect = prompt({
  id: "inspect-screenshot",
  input: z.object({ question: z.string() }),
  messages: ({ input }) => [
    {
      role: "user",
      content: [
        textPart(input.question),
        imagePart({ data: screenshotBytes, mediaType: "image/png" }),
        filePart({
          url: "https://example.com/brief.pdf",
          mediaType: "application/pdf",
          filename: "brief.pdf",
        }),
      ],
    },
  ],
});

const result = await generate(inspect, {
  model,
  input: { question: "What should change?" },
});

result.text;
result.messages;
```

Parts are plain JSON after construction. Binary data is base64, URLs are strings, and provider-specific per-part escapes live in `providerOptions`. Literal part objects are valid when you already have normalized data.

## Project to text

Use `messageText(message)` or `contentText(content)` for every string-only boundary:

```ts
import { contentText, imagePart, textPart } from "@use-crux/core";

const text = contentText([
  textPart("Review this image."),
  imagePart({ data: pngBytes, mediaType: "image/png" }),
]);
```

Text parts pass through verbatim. Images and files become bounded placeholders such as `[image image/png 210KB sha256:ab12...]` or `[file application/pdf "brief.pdf" https://example.com/brief.pdf]`. Raw base64 is never written into projections. Crux uses the same projection internally for guardrails, compaction, memory capture, semantic cache query text, resolver system messages, artifact previews, and telemetry.

## Adapter behavior

All first-party generation adapters accept the same canonical content. Provider support differs at the wire boundary:

| Capability | AI SDK | Anthropic | OpenAI Chat | Google |
| --- | --- | --- | --- | --- |
| Image input, data or URL | yes | yes | yes | yes |
| PDF input | yes | yes, document blocks | file data yes; URL degrades | yes |
| Audio input | model-dependent | degrades | wav/mp3 file data | yes |
| Assistant media decode | yes | yes | yes | yes |
| System role media | degrades everywhere | degrades everywhere | degrades everywhere | degrades everywhere |

Unsupported content degrades deliberately by default: Crux sends the text placeholder, emits a diagnostics warning, and records a `content.degraded` span event. Set `unsupportedContent: "error"` when a provider mismatch should fail before the wire call:

```ts
await generate(inspect, {
  model,
  input,
  unsupportedContent: "error",
});
```

The thrown `UnsupportedContentError` includes the part type, optional media type, role, and provider.

## Control is metadata

`ContentPart` is only for visible content. Tool calls, tool approvals, and other protocol/control signals live in `Message.metadata`. The AI SDK adapter normalizes SDK-shaped control parts into metadata before the rest of the harness sees the message, so guardrails and memory inspect user-visible content rather than transport protocol details.

## What stays text-only

`GenerateResult.text` and `StreamResult.textStream` stay string-shaped. Assistant-returned media is available in `result.messages`. Streamed media deltas, persistent storage externalization, media token estimation, and richer media descriptions are separate future surfaces; the v1 contract is canonical parts plus the bounded text projection.
