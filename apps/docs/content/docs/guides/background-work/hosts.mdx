Start with the [decision table](/docs/guides/background-work#do-i-need-to-set-anything-up)
if you have not read it: on most platforms `defer()` needs one config line or
nothing. This page is the per-platform detail — the recipe, why the platform
needs what it needs, and when to add the optional handler wrapper.

Application code always imports `defer` from `@use-crux/core` and never changes
per platform. Setup only tells Crux how *this* platform keeps the invocation
alive until deferred work settles.

## Next.js

**Setup: one line. Done.**

```ts title="crux.config.ts"
import { config } from "@use-crux/core";
import { next } from "@use-crux/next";

export default config({ host: next() });
```

Every `defer()` inside your agents, tools, and flows now survives the
invocation — drains still start at their own step's boundary; Next's `after()`
just keeps the function alive until they finish. Root-level `defer()` in plain
route code also works ambient, running after the response.

Add `withCrux` only for the [three wrapper cases](/docs/guides/background-work#when-is-the-config-line-not-enough)
(grouped root-level calls, handler outcome classification, strict commit
barrier) — it also installs the structured observability drain for the route:

```ts
import { defer } from "@use-crux/core";
import { withCrux } from "@use-crux/next";

export const POST = withCrux(async () => {
  defer(() => flushAnalytics());
  return Response.json({ ok: true });
});
```

## Vercel Functions (non-Next)

**Setup: one line. Done.**

```ts title="crux.config.ts"
import { config } from "@use-crux/core";
import { vercel } from "@use-crux/vercel";

export default config({ host: vercel() });
```

Retention rides `waitUntil()`, which starts retained work as soon as the
handler returns — deferred callbacks may overlap a still-streaming response
body. Use `withServerlessDefer` for the wrapper cases.

## Cloudflare Workers

**Setup: wrap the fetch handler.** Workers hand each request its own
`ExecutionContext`, and retention needs that exact `ctx` — this is the one
mainstream platform where a process-global config line cannot work:

```ts
import { defer } from "@use-crux/core";
import { withCrux } from "@use-crux/cloudflare";

export default {
  fetch: withCrux(
    async (_request, _env, _ctx) => {
      defer(() => flushAnalytics());
      return new Response("ok");
    },
    { context: (_request, _env, ctx) => ctx },
  ),
};
```

Building your own boundary instead? Construct `workers({ ctx })` per request
and pass it as the binding. `workers()` without a reachable context fails with
`DEFER_CAPABILITY_MISSING` — Crux does not accept work it cannot keep alive.

## Long-lived Node (servers, containers, VPS)

**Setup: nothing** for `defer()` inside Crux primitives — the process outlives
the work. For root-level `defer()` in raw HTTP handler code, wrap with
`withNodeDefer` so drains run after the response finishes:

```ts
import { createServer } from "node:http";
import { defer } from "@use-crux/core";
import { withNodeDefer } from "@use-crux/core/defer/node";

createServer(
  withNodeDefer(async (_request, response) => {
    defer(() => flushAnalytics());
    response.end("ok");
  }),
).listen(3000);
```

Multiprocess Node keeps inline work local to one worker; use
[durable work](/docs/guides/background-work#choosing-between-best-effort-and-durable)
when execution must survive or cross workers.

## AWS Lambda and other freeze-on-return hosts

**Setup: use durable work, not callbacks.** Lambda offers no way to run a
closure after the handler returns, so inline `defer(callback)` is rejected
explicitly rather than silently lost. Stage durable Runtime work instead:

```ts
export const handler = withNamedOnlyDefer(
  async (event: { id: string }) => {
    await defer(postProcess, { id: event.id }); // durable, survives the freeze
    return { ok: true };
  },
  { host: "lambda", durableFinalization: true },
);
```

## Convex

**Setup: none.** `createCruxConvex().run()` is the boundary. Like Lambda,
inline callbacks are rejected; use durable named work with `runtime: convex()`.

## Any other platform

Bring your own `CruxHostBinding` (how the platform keeps an invocation alive)
and either set it as `config({ host })` or wrap handlers with
`withServerlessDefer(handler, { binding })`. See
[Author a host adapter](/docs/guides/background-work/host-adapters).

## The matrix

| Environment | Setup | Inline `defer(callback)` | Durable `await defer(task, input)` | Optional strict wrapper |
| --- | --- | --- | --- | --- |
| Long-lived Node | none | ✓ process-local | ✓ with a Runtime | `withNodeDefer` |
| Next.js 15.1+ | `config({ host: next() })` | ✓ via `after()` | ✓ | `withCrux` / `withNextDefer` |
| Vercel Functions | `config({ host: vercel() })` | ✓ via `waitUntil()` | ✓ | `withServerlessDefer` |
| Cloudflare Workers | `withCrux` wrapper (per-request `ctx`) | ✓ via `ctx.waitUntil()` | ✓ | included in `withCrux` |
| AWS Lambda | `withNamedOnlyDefer` | ✗ rejected | ✓ Runtime required | `withNamedOnlyDefer` |
| Convex | none (bridge run) | ✗ rejected | ✓ `runtime: convex()` | bridge is the boundary |
| Custom | `CruxHostBinding` | binding-defined | ✓ with a Runtime | `withServerlessDefer` |

## Fine print for config-only mode

Without a wrapper, Crux has no request identity, so each root-level `defer()`
call in plain handler code gets its own ephemeral invocation and retention
task: correct timing and retention, but no cross-call grouping, no handler
outcome classification, and no strict commit barrier. Work inside Crux
primitives is unaffected — that is grouped by its real scope. This trade-off is
the entire content of the "three wrapper cases".
