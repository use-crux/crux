title: Background Work
description: Run follow-up work after your agent responds — without making the user wait, and without losing it on serverless.

## The problem

Almost every agent turn ends with work the user should not wait for:

- send the confirmation email, fire the webhook
- write analytics, usage metering, audit events
- update the search index, warm a cache
- persist memory or summarize the conversation

Doing this inline adds seconds to every response. The usual escapes are worse:
a fire-and-forget promise (`void doWork()`) dies silently on Vercel, Workers,
and Lambda the moment the invocation freezes; "after the response" hooks fire
at the wrong moment when your response is a stream; and a job queue is real
infrastructure for what is often one function call.

## The solution

```ts
import { defer } from "@use-crux/core";

const createAccount = tool({
  execute: async ({ email }) => {
    const user = await db.users.create({ email });

    defer(() => sendWelcomeEmail(user));   // runs after this tool finishes
    defer(() => track("signup", user.id)); // never delays the response

    return user;
  },
});
```

`defer(callback)` schedules work to start **when the current Crux step
finishes** — the tool call, agent turn, adapter call, or Safety session you are
already inside. The caller gets its result immediately; the work runs right
behind it; and Crux keeps the process alive until it settles.

Because Crux owns the boundary, the timing is right even where "after the
response" is wrong: work deferred during a streaming turn runs when the stream
actually completes, and work deferred in a tool starts when the tool finishes —
it does not wait for the rest of the request.

## Do I need to set anything up?

Usually not. The full decision:

| You run on | Setup | Why |
| --- | --- | --- |
| A long-lived server (Node, containers, a VPS) | **Nothing** | The process outlives the work |
| Next.js on Vercel | **One line:** `config({ host: next() })` | Serverless freezes after the response; the binding keeps it alive via `after()` |
| Vercel Functions (non-Next) | **One line:** `config({ host: vercel() })` | Same, via `waitUntil()` |
| Cloudflare Workers | **Wrap the handler** with `withCrux` from `@use-crux/cloudflare` | Workers scope retention to one request's `ctx`; config alone cannot reach it |
| AWS Lambda, Convex | **Skip inline callbacks** — use [durable work](#choosing-between-best-effort-and-durable) | These hosts offer no way to run closures after returning, and Crux refuses to pretend otherwise |

The one line, concretely:

```ts title="crux.config.ts"
import { config } from "@use-crux/core";
import { next } from "@use-crux/next";

export default config({ host: next() });
```

That is the whole setup. Every `defer()` inside your agents, tools, flows, and
Safety sessions now survives the platform. If you skip it where it is needed,
Crux throws (`DEFER_SCOPE_REQUIRED` / `DEFER_CAPABILITY_MISSING`) instead of
silently dropping your work — and `crux setup` tells you exactly which line to
add.

### When is the config line NOT enough?

Three specific situations — if none applies to you, stop here and use the table
above:

1. **You call `defer()` in plain handler code, outside any Crux primitive, and
   want those calls treated as one unit** (shared limits, one invocation in
   observability). Config-only mode runs each root-level call independently.
2. **You want a whole failed request to skip its deferred work.** Inside Crux
   primitives this is automatic per step; classifying the *handler's* HTTP
   outcome needs the handler boundary.
3. **You stage durable work and need the response to fail if staging fails**
   (a strict commit barrier).

All three are solved the same way — wrap the handler:

```ts
import { defer } from "@use-crux/core";
import { withCrux } from "@use-crux/next";

export const POST = withCrux(async () => {
  defer(() => flushAnalytics());
  return Response.json({ ok: true });
});
```

Wrappers are an upgrade for those cases, not a prerequisite. Platform recipes
and the full matrix live in [Host support](/docs/guides/background-work/hosts).

## Choosing between best-effort and durable

**`defer(callback)` is best-effort by design.** It runs in-process: fast, no
infrastructure, perfect for analytics, cache warming, notifications, cleanup —
work you would not page anyone over losing to a process crash.

**`await defer(task, input)` is for work you cannot afford to lose** — a
payment receipt, a legally required audit record. It stages the work durably
through the [Runtime Engine](/docs/guides/durable-execution), survives crashes
and restarts, and retries:

```ts
import { defer } from "@use-crux/core";
import { durableTask } from "@use-crux/core/runtime";

const sendReceipt = durableTask("send-receipt", {
  run: async (input: { orderId: string }) => emailReceipt(input.orderId),
});

const ref = await defer(sendReceipt, { orderId: order.id });
// resolves once the work is durably accepted; execution survives restarts
```

Durable targets can retry, so make them idempotent. This is also the only mode
that works on Lambda and Convex, where in-process callbacks cannot outlive the
handler.

## What you get without asking

- **Failure isolation.** A crashing callback is recorded and contained; it can
  never corrupt or replace the response the user already received.
- **Error-aware skipping.** Work deferred by a step that then fails is skipped
  (and recorded as skipped), so a failed signup never sends its welcome email.
- **Observability.** Every deferred callback — yours and Crux's own — shows up
  in the run's trace with its outcome, timing, and the scope that scheduled it.
- **Evals stay side-effect free.** Under `crux eval`, deferred work is captured
  as evidence instead of executing, so evaluating an agent never sends its
  emails.

## Inside replayable flows

Flow bodies replay; a bare `defer()` there would double-fire, so it throws
`DEFER_REPLAY_UNSAFE`. Use `flow.defer()`, which keeps stable identity across
replay:

```ts
await flow.defer(sendReceipt, { orderId: order.id });
```
