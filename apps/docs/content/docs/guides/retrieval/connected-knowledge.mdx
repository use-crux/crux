---
title: Connected Knowledge
description: Add typed relations to a knowledge base and expand retrieval through the resulting graph.
---

`knowledgeBase()` still starts as plain RAG: index documents, retrieve chunks, and use recipes only when you need extra query-time work.

```ts
import { knowledgeBase } from "@use-crux/core/knowledge";

const docs = knowledgeBase({
  id: "docs",
  storage,
  embeddings: dense,
});

const hits = await docs.retriever({ limit: 8 }).retrieve("refund policy");
```

Add connected knowledge when answers need nearby evidence that may not match the query text directly: cited specs, related product areas, prerequisite guides, or parent/child context.

## Add Pipeline Config

`knowledgeBase()` accepts an explicit indexing pipeline. Plain indexing stays unchanged until you put connected knowledge work in `derive`.

```ts
import { indexingPipeline } from "@use-crux/core/indexing";
import { knowledgeBase } from "@use-crux/core/knowledge";

const docs = knowledgeBase({
  id: "docs",
  storage,
  embeddings: dense,
  pipeline: indexingPipeline({
    derive: [productRelations],
  }),
});
```

Keep the pipeline close to the knowledge base when one corpus owns the relation vocabulary. Share the pipeline only when multiple knowledge bases should build the same graph shape.

## Author Relations

Use `relate()` to define a typed relation vocabulary. Each relation declares valid endpoint kinds, direction, and a short description.

Model mode uses `knowledgeModel()` to bind a stable name and fingerprint to a retrieval model surface:

```ts
import { knowledgeModel, relate } from "@use-crux/core/knowledge";

const extractor = knowledgeModel({
  name: "product-docs-relations",
  version: "2026-07-docs",
  generateText: retrievalModel.generateText,
  generateObject: retrievalModel.generateObject,
});

const productRelations = relate({
  id: "product-relations",
  version: 1,
  model: extractor,
  instructions: "Extract explicit citations and product-area mentions.",
  types: {
    cites: {
      from: ["chunk"],
      to: ["document"],
      direction: "directed",
      description: "A chunk cites another source document.",
    },
    mentionsArea: {
      from: ["chunk"],
      to: ["entity"],
      direction: "directed",
      description: "A chunk mentions a product area.",
    },
  },
});
```

Use deterministic run mode when your app can produce relations from rules, metadata, or parsed content:

```ts
const productRelations = relate({
  id: "product-relations",
  version: 1,
  types: {
    mentionsArea: {
      from: ["chunk"],
      to: ["entity"],
      direction: "directed",
      description: "A chunk mentions a product area.",
    },
  },
  run: ({ chunks }, api) => {
    for (const chunk of chunks) {
      if (!chunk.content.includes("Billing")) continue;

      const evidence = {
        kind: "chunk",
        sourceId: chunk.sourceId,
        chunkId: chunk.chunkId,
      } as const;

      api.emit("mentionsArea", evidence, { kind: "entity", entityId: "billing" }, { evidence });
    }
  },
});
```

The `api.emit()` call is typed by the vocabulary. A `mentionsArea` relation must start at a `chunk` and end at an `entity`; TypeScript rejects other endpoint kinds.

## Expand Retrieval

Use `expandRelations()` inside `docs.recipe()` after `retrieve()`. The step starts from retrieved chunks, traverses visible graph neighbors, hydrates any added chunk refs, and appends them to the hit list.

```ts
import { expandRelations, retrieve } from "@use-crux/core/retrieval";

const answerDocs = docs.recipe({
  id: "docs-answer",
  steps: [
    retrieve({ limit: 12 }),
    expandRelations({
      types: ["mentionsArea", "hierarchy"],
      direction: "both",
      depth: 2,
      limit: 8,
    }),
  ],
});

const hits = await answerDocs.retrieve("how do billing limits affect teams?");
```

`expandRelations()` accepts:

| Option      | Default           | Meaning                                          |
| ----------- | ----------------- | ------------------------------------------------ |
| `types`     | all visible types | Relation type names to traverse.                 |
| `direction` | `"both"`          | Traverse outgoing, incoming, or both directions. |
| `depth`     | `1`               | Maximum semantic hop distance.                   |
| `limit`     | `20`              | Maximum unique added hits.                       |

Added hits include graph provenance:

```ts
const expanded = hits.find((hit) => hit.provenance?.graph);

expanded?.provenance?.graph;
// {
//   seed: "chunk:guide:c1",
//   path: ["chunk:guide:c1", "entity:billing", "chunk:limits:c4"],
//   edges: ["mentionsArea", "mentionsArea"],
//   distance: 1
// }
```

`seed` is the encoded ref that discovered the hit. `path` is the encoded traversal path. `edges` are the relation types followed along the path. `distance` is the semantic hop distance used for ordering and limits.

## Global Search

Use `globalSearch()` when the query should scan Connected Knowledge community reports instead of starting from vector hits. Configure communities on the knowledge base, prepare them when you want to prewarm the materialization, then use `globalSearch()` as the recipe's single producer step.

```ts
import { communities, knowledgeBase } from "@use-crux/core/knowledge";
import { globalSearch } from "@use-crux/core/retrieval";

const docs = knowledgeBase({
  id: "docs",
  storage,
  communities: communities({ model }),
});

await docs.communities?.prepare();

const reportSearch = docs.recipe({
  id: "docs-report-search",
  steps: [
    globalSearch({
      model,
      detail: "overview",
      scan: "all",
      limit: 12,
    }),
  ],
});

const findings = await reportSearch.retrieve("which launch risks affect billing?");
```

`globalSearch()` returns finding hits. Evidence hits keep `source`, `chunkId`, and `metadata`; finding hits use `kind: "finding"` and carry a citation with an issued `findingTarget`, transitive evidence supports, assertion refs, and community lineage.

```ts
for (const hit of findings) {
  if (hit.kind === "finding") {
    console.log(hit.content, hit.citation.findingTarget);
  } else {
    console.log(hit.source.id, hit.chunkId);
  }
}
```

A retrieval recipe can have only one producer step: use either `retrieve()` or `globalSearch()`. Request filters are rejected for global search because reports may summarize evidence outside the filter. Use a typed view for narrowing:

```ts
const published = docs.view({
  id: "published",
  where: { status: "published" },
});

const publishedReportSearch = published.recipe({
  steps: [globalSearch({ model, detail: "detailed" })],
});
```

The recipe trace includes a knowledge receipt with the coverage path (`"exact"`, `"compensated"`, `"raw-fallback"`, or `"materialization-wait"`), selected detail, scan mode, processed report counts, preflight estimate, and adaptive descent trace when `scan: "adaptive"` is used.

## Live Views

Use `metadataSchema` when a knowledge base has stable source metadata you want to address as a read surface. `view({ id, where })` is typed by that schema and stays live as matching sources are indexed, reindexed, or removed.

```ts
import { z } from "zod";
import { knowledgeBase } from "@use-crux/core/knowledge";

const metadataSchema = z.object({
  status: z.enum(["draft", "published", "archived"]),
  team: z.string(),
  priority: z.enum(["normal", "high"]),
});

const docs = knowledgeBase({
  id: "docs",
  storage,
  embeddings: dense,
  metadataSchema,
});

const publishedDocs = docs.view({
  id: "published-docs",
  where: {
    status: "published",
    team: ["docs", "support"],
  },
});
```

Array values are exact `IN` matches. Use `{ any: [...] }` for a union of compound clauses:

```ts
const responseDocs = docs.view({
  id: "response-docs",
  where: {
    any: [
      { status: "published", priority: "high" },
      { status: "published", team: "support" },
    ],
  },
});
```

Views expose the same read shape as a knowledge base:

```ts
const hits = await publishedDocs.retriever({ limit: 8 }).retrieve("billing limits");

const answerDocs = publishedDocs.recipe({
  steps: [
    retrieve({ limit: 8 }),
    expandRelations({ types: ["mentionsArea"], direction: "both" }),
  ],
});
```

Membership is authoritative. The portable vector path may push exact metadata filters down into storage, but every returned hit is still checked against the resolved view membership before it is returned. A storage optimization can collapse that into a membership-aware query without changing the result contract.

Resolve a view when you need a replayable member set:

```ts
const revision = await publishedDocs.resolve();
const pinnedDocs = publishedDocs.at(revision.revisionHash);

const replayHits = await pinnedDocs.retriever({ limit: 8 }).retrieve("billing limits");
```

The live handle sees the next revision when matching sources change. A pinned handle replays the exact revision and fails if a member source is no longer exactly available.

Scopes isolate live views and their revisions by namespace:

```ts
const tenantDocs = docs.scope({ namespace: "tenant-a" });

const tenantPublished = tenantDocs.view({
  id: "published-docs",
  where: { status: "published" },
});
```

The same view id can exist in another namespace without sharing members, graph traversal, or hydrated hits.

## Assertions

Use `assertions()` when indexing should publish typed propositions with evidence supports. Assertion data is described by Zod schemas; evidence must point at indexed chunks.

```ts
import { z } from "zod";
import { assertions } from "@use-crux/core/knowledge";

const productFacts = assertions({
  id: "product-facts",
  version: 1,
  types: {
    limit: z.object({
      name: z.string(),
      value: z.string(),
    }).describe("A documented product limit."),
  },
  run: ({ chunks }, api) => {
    for (const chunk of chunks) {
      if (!chunk.content.includes("100 projects")) continue;

      api.emit("limit", {
        name: "project-count",
        value: "100 projects",
      }, {
        evidence: {
          kind: "chunk",
          sourceId: chunk.sourceId,
          chunkId: chunk.chunkId,
        },
        provenance: "exact",
      });
    }
  },
});
```

Add assertion stages to the same `derive` pipeline as relations:

```ts
const docs = knowledgeBase({
  id: "docs",
  storage,
  pipeline: indexingPipeline({
    derive: [productFacts],
  }),
});
```

Read assertions from either a knowledge base or a view. The `types` option narrows the returned item type:

```ts
const limits = docs.assertions(productFacts, {
  types: ["limit"],
});

const page = await limits.list({ limit: 25 });

for await (const assertion of limits.stream()) {
  console.log(assertion.data.name, assertion.evidence);
}
```

View-bound assertion sets resolve the view first. Supports outside the pinned revision are excluded; assertions with no visible supports are hidden.

Assertion sets can also be composed into prompts. The injected context is a compact, bounded summary rather than raw assertion records:

```ts
const answer = prompt({
  use: [publishedDocs.assertions(productFacts, { types: ["limit"] })],
  system: "Answer from the documented product facts.",
});
```

Assertion stages can also relate assertions they emit in the same source run, or canonical assertion identities they compute:

```ts
run: ({ chunks }, api) => {
  const evidence = {
    kind: "chunk",
    sourceId: chunks[0].sourceId,
    chunkId: chunks[0].chunkId,
  } as const;

  const current = api.emit("limit", {
    name: "project-count",
    value: "100 projects",
  }, { evidence });

  api.relate("supersedes", current, {
    type: "limit",
    data: { name: "project-count", value: "75 projects" },
  }, { evidence });
}
```

Resolve a set to apply explicit assertion relations such as `supersedes` and `conflictsWith`:

```ts
const resolved = await docs.assertions(productFacts).resolve().result();

resolved.selected;
resolved.superseded;
resolved.contested;
resolved.trace;
```

You can pass a resolution handle through `use` when a prompt should see the selected partition plus counts for superseded, contested, and unresolved assertions:

```ts
const resolvedFacts = publishedDocs.assertions(productFacts).resolve();

const answer = prompt({
  use: [resolvedFacts],
  system: "Prefer selected facts and account for unresolved items.",
});
```

Resolution never mutates the source assertions. Assertion relations are separate records, not graph edges, so `expandRelations()` does not traverse assertion supports or assertion relations.

## Communities

Use `communities()` when a knowledge base should materialize a browsable topic map over its connected graph. Communities cluster visible entities, attach every visible chunk to exactly one leaf, and publish structured reports you can read from the knowledge base or from a view.

```ts
import { communities, knowledgeBase, knowledgeModel } from '@use-crux/core/knowledge'

const reporter = knowledgeModel({
  name: 'docs-community-reports',
  version: '2026-07-docs',
  generateText: retrievalModel.generateText,
  generateObject: retrievalModel.generateObject,
})

const docs = knowledgeBase({
  id: 'docs',
  storage,
  communities: communities({ model: reporter }),
})
```

`prepare()` builds or refreshes the materialization. `status()` reports whether the current generation is missing, building, ready, or stale:

```ts
await docs.index(sources)

await docs.communities?.status()
await docs.communities?.prepare()

const page = await docs.communities?.reports({ level: 0, limit: 25 })
```

Views expose the same surface, scoped to the resolved revision:

```ts
const published = docs.view({
  id: 'published-docs',
  where: { status: 'published' },
})

await published.communities?.prepare()

const children = await published.communities?.reports({
  parentId: 'community_abc123',
  limit: 20,
})
```

If no entity relation stage is configured, communities run the built-in generic entity mapping pass through the same connected knowledge pipeline used by `relateEntities()`. If you already authored `relateEntities({ model })`, that published graph is reused as the community input.

Reports are generation-scoped records. A failed refresh never replaces the prior published generation, and unchanged communities reuse their prior report content during later refreshes.

## What Runs When

Plain `knowledgeBase()` indexing and retrieval behave as before. Passing a pipeline adds the connected knowledge work you configured.

No model calls happen unless a relation vocabulary or communities are configured with an explicit `model` from `knowledgeModel()`. Deterministic `run` relations execute from your code during indexing.

`expandRelations()` runs at query time inside the retrieval recipe. It reads the graph visible to that knowledge base and does not create new relations.

Virtual structural relations are always available from indexed records. Parent/child hierarchy and chunk sequence can be traversed by `expandRelations()` even when you have not authored a relation vocabulary.
