## Overview

`defer` is a dual overload on the package root. Prefer overloads over casts:
named targets come first; unbranded callbacks select the inline form.

## `defer(callback)`

| Parameter  | Type                              | Description                 |
| ---------- | --------------------------------- | --------------------------- |
| `callback` | `() => void \| PromiseLike<void>` | Lazy zero-argument callback |

**Returns:** `void`

Registers work on the nearest compatible execution scope. The callback starts
when that scope closes and its host binding releases retained work. Failures are
contained and observed; they do not fail an already-committed response.

Agent turns, adapter calls, tool executions, and Safety sessions install this
scope automatically. On a long-lived process, `defer(callback)` therefore needs
no wrapper or host configuration inside those primitives. Nested registrations
belong to the nearest primitive, so their evidence and drain timing stay local.
Replayable flow steps remain guarded and require `flow.defer()`.

Throws:

- `DEFER_SCOPE_REQUIRED`: no active scope
- `DEFER_CAPABILITY_MISSING`: scope lacks inline support
- `DEFER_SCOPE_SEALED` / `DEFER_LIMIT_EXCEEDED`: lifecycle bounds
- `DEFER_REPLAY_UNSAFE`: inside replayable flow execution

## `defer(target, input)`

| Parameter | Type                        | Description                                        |
| --------- | --------------------------- | -------------------------------------------------- |
| `target`  | branded `RuntimeTaskTarget` | Exported `durableTask(...)` (or compatible) target |
| `input`   | inferred JSON-safe input    | Required for V1 targets constrained to `JsonValue` |

**Returns:** `Promise<DeferredWorkRef>`

```ts
interface DeferredWorkRef {
  readonly kind: "deferred.work";
  readonly workId: string;
  readonly targetId: string;
}
```

Resolves after durable staging acceptance. Execution still waits for successful
logical finalization and outbox release. Host adapters must await the scope
`committed` barrier before committing the response.

Throws or poisons commit with:

- `RUNTIME_REQUIRED` (cause) / `DEFER_COMMIT_FAILED` (host barrier)
- `DEFER_CAPABILITY_MISSING` when the host cannot finalize named work
- `DEFER_TARGET_INPUT_REQUIRED` for missing input at runtime
- `DEFER_REPLAY_UNSAFE` inside replayable flows

## Host binding semantics

### Retention timing

The host binding decides when retained inline callbacks may start relative to
the response:

- Node HTTP and Next.js `after()` release callbacks after response completion.
- `waitUntil` bindings may release callbacks when the handler returns, so work
  can overlap a still-streaming response body.
- Named-only bindings (Lambda `withNamedOnlyDefer`, Convex bridge runs) reject
  inline `defer(callback)` with
  `DEFER_CAPABILITY_MISSING`.

### `durableFinalization` advertisement

A host binding advertises `durableFinalization: true` only when it can await
the named-defer commit barrier before committing the response. Named
`await defer(target, input)` requires a configured Runtime plus a binding
advertising durable finalization; raw Node hosts advertise
`durableFinalization: false` unless the wrapper opts in (for example
`withNamedOnlyDefer(handler, { durableFinalization: true })`).

### Capability is explicit, never inferred

Never infer host correctness from environment variable names (`VERCEL`, etc.).
Capability comes only from the wrapper or platform binding that is explicitly
installed (`waitUntil`, `after`, `next()`, `workers()`, or `vercel()`); an
installed package or recognizable environment alone proves nothing.
