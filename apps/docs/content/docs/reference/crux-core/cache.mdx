Import from the cache subpath:

```ts
import {
  createSemanticCache,
  semanticCachePolicies,
} from "@use-crux/core/cache";
```

## `createSemanticCache(config)`

Creates a Crux plugin that wraps `generate()` and `stream()` calls for prompts that opt into `cache.semantic`.

```ts
createSemanticCache({
  store,
  embedding,
  ttl: 60_000,
  threshold: 0.95,
  scope: ({ input }) => `tenant:${input.tenantId}`,
});
```

Required fields:

| Field       | Description                                                                                    |
| ----------- | ---------------------------------------------------------------------------------------------- |
| `store`     | `RecordStore` with TTL, dense vector search, and isolated semantic-cache namespace capability. |
| `embedding` | `DenseEmbedding`. Sparse and fused lookup are intentionally not accepted.                      |
| `ttl`       | Maximum cache lifetime in milliseconds. Must be greater than zero.                             |
| `scope`     | `'global'` or a function returning a safety boundary string.                                   |

Optional fields:

| Field          | Description                                                        |
| -------------- | ------------------------------------------------------------------ |
| `threshold`    | Minimum similarity score. Defaults to `0.95`.                      |
| `namespace`    | Logical cache namespace inside the store. Defaults to `'default'`. |
| `shouldLookup` | Callback that can skip lookup.                                     |
| `shouldCache`  | Callback that can skip writes after generation.                    |

Prompt-level `cache.semantic` can set `mode`, `version`, `ttl`, `threshold`, and `query`. Prompt TTLs only shorten the plugin TTL. Prompt thresholds only make matching stricter.

## `semanticCachePolicies`

Built-in policy helpers:

| Helper                       | Use                                             |
| ---------------------------- | ----------------------------------------------- |
| `finishReason(...allowed)`   | Cache only selected finish reasons.             |
| `noErrors()`                 | Cache only when no error is present.            |
| `promptIds(ids)`             | Apply lookup/write only to specific prompt ids. |
| `skipWhenToolsPresent()`     | Disable lookup when tools are available.        |
| `skipWhenToolCallsPresent()` | Disable writes when the model used tools.       |
| `all([...])`                 | Compose policies with AND.                      |
| `any([...])`                 | Compose policies with OR.                       |
| `not(policy)`                | Negate a policy.                                |

## Policy Callbacks

Custom `shouldLookup` and `shouldCache` callbacks receive the prompt id, operation, input, prepared provider arguments, tools presence, version, and threshold. `shouldCache` additionally receives the generated result on write.

## Dense-Only Embeddings

`createSemanticCache()` accepts a `DenseEmbedding` only; sparse embeddings and fused retrieval plans are rejected.

Sparse and multi-leg retrieval are supported elsewhere in Crux through `retriever()` and `SearchStore.search()`, and they are excellent for document search. Response caching has a different job: decide whether a completed prompt result can be reused. That decision needs a single threshold with predictable meaning. Multi-leg retrieval introduces fusion choices and adapter-specific ranking behavior, which makes a default response-cache threshold misleading.

If you need sparse or fused cache lookup, implement it as a custom cache or retrieval policy. Crux does not block that pattern; it only avoids presenting it as the default semantic response cache.

## Events

Instrumentation hooks include:

```ts
onSemanticCacheLookupStart;
onSemanticCacheLookupEnd;
onSemanticCacheHit;
onSemanticCacheMiss;
onSemanticCacheWrite;
onSemanticCacheSkip;
onSemanticCacheReplayStart;
onSemanticCacheReplayEnd;
```

The devtools wire protocol uses matching `semantic-cache:*` event names.

## Store Capability Rule

`createSemanticCache()` refuses stores that cannot prove both requirements:

```ts
records.capabilities().ttl !== false; // record store must support TTL
search.capabilities().filter === "pre"; // search store must pre-filter
```

This is deliberate. Cache entries expire through record-store TTL, and lookups scope by namespace and version before ranking, so a search store that only post-filters can let unrelated records crowd out cache entries. Keep semantic-cache entries in a dedicated search namespace/index rather than sharing one with memory or RAG chunks.

`inMemoryStorage()` satisfies both by default. Durable adapters qualify when the record store supports TTL and the search backend applies filters before ranking. Plain Redis stores do not expose search unless product-specific search hooks are configured.

Convex bundled storage provides records but not search. Pair `convexRecordStore()` with an explicit pre-filter-capable `SearchStore`, such as `upstashSearchStore()` in a dedicated semantic-cache namespace.
