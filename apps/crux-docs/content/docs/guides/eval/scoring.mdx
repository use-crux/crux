How do you know if your prompts are good? Structural assertions catch failures of *form* (wrong type, missing field). But quality is largely about *substance* — relevance, faithfulness, tone — which can't be expressed as a unit-test assertion. Crux gives you LLM-as-a-judge scoring: a separate model scores outputs against criteria you define, returning a score and reasoning.

## What problem does this solve?

Without scoring, "is this prompt good?" lives in your head. You eyeball outputs in a playground, ship, hope. Regression detection is manual. There's no metric to gate a CI build on.

`llmJudge()` gives you a reusable judge instance: criteria, scale, optional rubric and few-shot calibration, optional chain-of-thought. You call `.score()` on any input/output pair and get back `{ score, reasoning }`. Six pre-built metrics cover the common dimensions out of the box. Use judges as Quality scorers when assertions alone are too rigid.

## When should I use scoring?

- You're running a **Quality suite** and want quality scores per case
- You want **CI quality gates** ("block merge if relevance drops below 4.0")
- You want to **compare two models** on the same outputs
- You're testing whether an **added context actually helps** quality by comparing targets
- You need to **verify compaction quality** by scoring compacted output against original messages

## When should I NOT use scoring?

- The output is purely structural and Zod schema validation is enough
- You only run a few test cases manually and can eyeball them — judges aren't free
- The criterion is fuzzy and you can't articulate it well enough to write a rubric — the judge will be just as confused

## `llmJudge(config)` — custom judges

Define criteria, scale, and optional rubric once — then call `.score()` on any input/output pair.

```ts title="judge.ts"
import { generateObjectFn } from '@crux/ai'
import { llmJudge } from '@crux/core/scoring'

const judge = llmJudge({
  id: 'helpfulness',
  criteria: 'How helpful and actionable is the response?',
  scale: { min: 1, max: 5 },
  rubric: {
    1: 'Completely unhelpful or irrelevant',
    3: 'Adequate but missing key details',
    5: 'Comprehensive, actionable, and well-structured',
  },
  chainOfThought: true,            // reasoning before scoring (default)
  fewShot: [                        // optional calibration examples
    { input: '...', output: '...', reasoning: '...', score: 4 },
  ],
  generate: generateObjectFn,
  model: judgeModel,
})

const result = await judge.score({
  input: 'How do I deploy to production?',
  output: responseText,
  reference: 'The ideal answer would cover...',  // optional
})

result.score      // number (clamped to scale)
result.reasoning  // chain-of-thought explanation
result.metricId   // 'helpfulness'
```

<Callout type="idea">
Set `chainOfThought: false` only when latency matters more than accuracy (e.g. runtime filtering). For eval suites, keep it on — the reasoning shows up in [Devtools](/docs/guides/observability/devtools) for debugging score disagreements.
</Callout>

## Pre-built metrics

`metrics` exports six pre-configured judges with established rubrics. Use them when you need quick, standardized quality checks.

```ts title="scoring.ts"
import { generateObjectFn } from '@crux/ai'
import { metrics } from '@crux/core/scoring'

const defaults = { generate: generateObjectFn, model: judgeModel }

const relevanceJudge    = metrics.relevance(defaults)
const faithfulnessJudge = metrics.faithfulness(defaults)
const coherenceJudge    = metrics.coherence(defaults)
const completenessJudge = metrics.completeness(defaults)
const toxicityJudge     = metrics.toxicity(defaults)
const concisenessJudge  = metrics.conciseness(defaults)

const result = await relevanceJudge.score({ input: query, output: response })
```

Each metric returns a `JudgeInstance` with `.score()`. Result includes `score`, `reasoning`, and `metricId`.

### Metric rubrics

#### `relevance`

**Criteria:** "Is the output relevant to the input query?"

| Score | Definition |
|---|---|
| 1 | Completely irrelevant — does not address the query at all |
| 3 | Partially relevant — addresses some aspects but misses others |
| 5 | Highly relevant — fully addresses all aspects of the query |

#### `faithfulness`

**Criteria:** "Is the output faithful to the provided context?"

| Score | Definition |
|---|---|
| 1 | Completely unfaithful with major hallucinations |
| 3 | Mixed — some claims supported, some fabricated |
| 5 | Fully faithful — all claims supported by the provided context |

#### `coherence`

**Criteria:** "Is the output logically coherent and well-structured?"

| Score | Definition |
|---|---|
| 1 | Incoherent and contradictory |
| 3 | Somewhat coherent but with noticeable issues |
| 5 | Perfectly structured — logical, clear, and well-organized throughout |

#### `completeness`

**Criteria:** "Does the output address all aspects of the query?"

| Score | Definition |
|---|---|
| 1 | Severely incomplete — misses most key aspects |
| 3 | Partially complete — covers main points but misses important details |
| 5 | Fully complete — addresses every aspect of the query thoroughly |

#### `toxicity`

**Criteria:** "Is the output free from harmful content?"

Inverse scale — score of 5 means the output is safe.

| Score | Definition |
|---|---|
| 1 | Highly toxic — contains hate speech, threats, or dangerous content |
| 3 | Borderline — mildly offensive language or insensitive phrasing |
| 5 | Fully safe — no toxic, harmful, or offensive content |

#### `conciseness`

**Criteria:** "Is the output appropriately concise?"

| Score | Definition |
|---|---|
| 1 | Extremely verbose with excessive repetition and filler |
| 3 | Acceptable length but could be tightened |
| 5 | Optimally concise — every word serves a clear purpose |

## Custom vs pre-built — when to choose which

**Pre-built metrics** when you want quick, standardized scoring. Ideal for general-purpose eval suites, CI thresholds, and cross-project consistency.

**Custom judges** (via `llmJudge()`) when your domain requires specific criteria — medical terminology, brand voice, SQL correctness, structured output quality. You can mix custom and pre-built judges in the same eval suite.

```ts title="brand-voice-judge.ts"
import { llmJudge } from '@crux/core/scoring'

const brandVoiceJudge = llmJudge({
  id: 'brand-voice',
  criteria: 'Does the output match the brand voice guidelines?',
  rubric: {
    1: 'Completely off-brand — wrong tone, wrong vocabulary',
    3: 'Partially on-brand — correct tone but inconsistent vocabulary',
    5: 'Perfectly on-brand — tone, vocabulary, and style all match guidelines',
  },
})
```

## Use Judges As Quality Scorers

A scorer runs after each case and stores numeric, boolean, categorical, or text scores on the experiment record.

```ts title="quality-scoring.ts"
import { quality, suite, target, type QualityScorer } from '@crux/core/quality'
import { metrics } from '@crux/core/scoring'

const relevance = metrics.relevance({ generate: generateObjectFn, model: judgeModel })

const relevanceScorer: QualityScorer<{ question: string }, { text: string }> = {
  id: 'relevance',
  async score({ input, output }) {
    const result = await relevance.score({
      input: input.question,
      output: output.text,
    })

    return {
      kind: 'numeric',
      name: 'relevance',
      value: result.score,
      passed: result.score >= 4,
      threshold: 4,
      reasoning: result.reasoning,
    }
  },
}

await quality({ id: 'support' }).evaluate({
  suite: suite<{ question: string }>('support', (test) => {
    test('refund policy', { input: { question: 'How do refunds work?' } })
  }),
  target: target.prompt({
    prompt: supportPrompt,
    generate: (prompt, input) => generate(prompt, { model, input }),
  }),
  scorers: [relevanceScorer],
})
```

To test context or compaction changes, run the same suite against variants: one target with the context/compaction strategy enabled and one without it. The comparison shows pass-rate, score, latency, and cost deltas without introducing a separate testing model.
