# Connected Knowledge portability and lifecycle plan

## Scope and invariants

- Keep `@use-crux/core` provider-neutral. Preserve the authored `assertions()` Zod schemas as the final validator; provider wire schemas are an internal compilation product.
- Keep one model call per bounded assertion batch, not per assertion type. Do not change ECO relation schemas.
- Update the existing `.changeset/assertion-provenance.md` and `.changeset/connected-knowledge-foundations.md`; do not create a changeset. Both already cover the published Core behavior and documentation theme.

## Internal community policy (version 2)

Implement this in a new internal `packages/core/src/knowledge/communities/assertion-policy.ts`, included in `COMMUNITY_STRATEGY_VERSION`'s fingerprint input.

- Deduplicate an assertion's visible supports by encoded chunk ref. Give each exact support base weight 2 and each derived support base weight 1; divide each base weight by the assertion's total base weight. Then group visible assertions by `stageId` and divide each assertion's aggregate clustering mass by that stage's visible assertion count. Each stage therefore contributes at most `1.0` total assertion affinity regardless of extraction volume, while report membership remains unweighted.
- Convert each support chunk to its already assigned leaf community, sum the assertion-local normalized support weights per leaf, and choose the primary leaf by descending score then lexical `communityId`. Keep every other leaf with positive distinct support as a secondary membership, ordered by descending score then lexical `communityId`. Primary membership alone contributes clustering weight, input budget, and canonical `assertion:<assertionId>` membership identity; secondary membership is report availability/counting only.
- Before leaf clustering, derive assertion-to-entity affinity from entities mentioned on visible support chunks: split the stage-normalized support mass equally among the distinct entities on that chunk, convert one assertion's entity affinities to unordered entity-pair weights with `min(left, right)`, and renormalize its pair weights to that assertion's stage-normalized mass. Add these weights to existing entity edges. Do not create affinity merely because assertions share a source document.
- After membership, assign raw inter-community relation roles `supports: 1`, `amends: 2`, `narrows: 2`, `supersedes: 3`, and `conflictsWith: 3`. Retain a relation only when both endpoints are visible. Normalize each relation to `raw / max(total raw incident weight at from, total raw incident weight at to)`; this symmetrically caps every assertion endpoint's relation influence at `1.0`. Internal relations are report context only; cross-community relations affect parent grouping, not leaf formation or primary membership. Sort boundary summaries by normalized weight descending then `relationId` and cap each leaf prompt at 20.

## Phase 1 — portable assertion wire compiler

1. Add `packages/core/src/knowledge/derive/assertion-wire.ts` as the sole compiler/decoder boundary. It will deterministically sort `AssertionStage.types`, assign `type_0`, `type_1`, etc., and return a frozen manifest containing slot, authored type, profile (`typed` or `json-string`), compiled Zod wire schema, and diagnostic reason for each fallback. Include a named wire compiler version in the manifest/fingerprint input.
2. Recursively inspect authored Zod JSON Schema output rather than exposing Zod internals. Accept only closed required objects, homogeneous arrays, scalar/string-or-number enum values, bounded depth/size, and descriptions. Reject unions, optional/nullable fields, arbitrary-key objects, composition keywords, transforms/refinements, and unsupported constraints for typed slots. Typed objects must be closed and have every property in `required`; fallback slots expose only required `dataJson: string`, generic evidence, and required lowercase provenance enum.
3. Replace `payloadSchema()` and the generated read path in `packages/core/src/knowledge/derive/assertion-runner.ts` with the compiler. Render slot-specific instructions through `renderBoundedAssertionBatches()` in `packages/core/src/knowledge/derive/prompt-bounds.ts`: required slots/empty arrays, no cross-slot or cross-batch duplicates, target-only evidence, provenance, and JSON fallback encoding. Decode per manifest, restore canonical `type`, locally parse `dataJson`, validate authored schemas/evidence/provenance through `validateAssertionClaims()`, and retain valid claims while repair feedback names only invalid slots and paths.
4. Include compiler version and stable manifest representation in model-stage identity in `packages/core/src/knowledge/assertions/assertions.ts`; bump `EXTRACTION_CONTRACT_VERSION` in `packages/core/src/knowledge/derive/bounds.ts` so prior claim manifests cannot be reused. Keep `ClaimManifestRecord` and `isCurrentManifest()` in `packages/core/src/knowledge/derive/manifest.ts` as the cache gate.
5. Write red tests first in `packages/core/__tests__/knowledge/assertion-wire-schema.test.ts` and `packages/core/__tests__/knowledge/assertions.test.ts`, then implement: multiple kinds in one call, stable sorted slots independent of authored key order, all-required/closed portable schema, descriptions/enums, mixed typed and JSON fallback diagnostics, forbidden-profile recursion, target validation, canonical deduplication, and slot-scoped repair that preserves a valid first-attempt claim.

## Phase 2 — assertion-aware graph, memberships, and reports

1. Extend the internal graph contracts in `packages/core/src/knowledge/communities/types.ts` and normalization in `cluster-normalize.ts` with assertion inputs, primary/secondary memberships, assertion/entity affinities, and visible internal/boundary assertion-relation summaries. Keep public `communities()` configuration unchanged.
2. Extend `buildCommunityGraphInput()` in `packages/core/src/knowledge/communities/graph-input.ts` to read current `KnowledgeAssertionRecord`s and `AssertionRelationRecord`s alongside entities/edges. Filter supports to visible chunks (including pinned views), calculate the policy above, discard assertions without admissible support, calculate primary membership inside that projection, and expose a relation only when both endpoint assertions are visible; classify it as internal or boundary by endpoint primary communities.
3. Update `cluster.ts` to place every visible assertion in its primary leaf's canonical member identities and use only primary assertion/entity affinity plus bounded relation weights for clustering and parent-tree links. Secondary memberships must not alter IDs, leaf size, or clustering. Extend `cluster-split.ts`/`cluster-parents.ts` only where their typed edge/member inputs need the new weighted links; retain their deterministic ordering and budget checks.
4. Update `reports.ts`, `report-schema.ts`, and `records.ts` so leaf prompts receive canonical assertions, member chunks/entities, internal relations, and bounded cross-community summaries; parent prompts aggregate child evidence. Validate finding assertion refs against that report's projection. Calculate leaf counts from identity sets (entities, chunks, assertions where primary or secondary member) and parent counts by unioning descendant identity sets, never summing child counters. Add assertion/relation projection and report-prompt version to `memberHashFor()`.
5. Bump `COMMUNITY_STRATEGY_VERSION` in `communities.ts` to 2 and hash the policy constants plus a report-prompt version in `strategyFingerprint`; this invalidates report reuse and current pointers whenever the new projection changes output. No Project Index or Eval-evidence epoch changes are needed: this is a Core connected-knowledge materialization identity change, not Project Index output or Eval evidence identity.
6. Write red tests first in `packages/core/__tests__/knowledge/communities-cluster.test.ts` and `communities-build.test.ts`, adding narrowly scoped fixtures as needed: exact/derived normalized weights, deterministic primary tie break, secondary threshold/no double clustering influence, relation hierarchy effect, assertion-volume normalization, view recomputation and boundary filtering, assertion-aware prompt/ref validation, identity counts at leaf/parent, and report cache misses when assertion projection or policy/prompt version changes.
