01 · Mental model

Five concepts for the normal path.

Tasks and prompts already exist in the application. Evals add only the familiar testing concepts around them.

01

Eval

A test definition: one task, some cases, and the checks that describe acceptable behavior.

evaluate({ … })
02

Case

One example input, plus optional expected data. Inline for small evals; reusable datasets when useful.

{ input, expected? }
03

Variant

A named candidate change—prompt, model, settings, or task—that runs over the same cases.

variants: { cheaper: … }
04

Eval run

The persisted result of running an eval. It contains outcomes, scores, cost, provenance, and comparison.

crux eval support
05

Baseline

A deliberately accepted historical run. It answers: did today become worse than the past we trusted?

baseline set

Current is implicit. It simply means the task referenced by the eval as it exists today. Users never define a current variant.

Cache is not a concept. Reports say “reused” or “new” and explain why. Users control it only with --fresh and --offline.

The definition

An eval is just this formula.

Scorers, judges, fingerprints, repeated samples, and traces are capabilities behind these three understandable ingredients.

02 · First run

Write one file. Run one command.

No executor setup. No cassette mode. No .run() method on the definition. The task already knows how production executes.

1

Reference the real task

The eval does not repeat its prompt, model, stream mode, or routing.

2

Add representative cases

Inputs are typed from the task. Expected data is optional.

3

Run from the CLI

crux eval support discovers and executes the definition.

4

Change and rerun

Crux computes only work whose inputs changed.

5

Set a baseline when trusted

Optional until a relative regression gate actually needs it.

production task + evalone definition, then test it
// src/support.ts — normal production behavior
import { generate } from '@use-crux/ai'
import { supportRouter } from './models'
import { supportPrompt } from './prompts'

export const support = generate.task(supportPrompt, {
  model: supportRouter,
  temperature: 0.2,
})

// evals/support.eval.ts — auto-discovered as support
import { evaluate } from '@use-crux/core/eval'
import { support } from '../src/support'
import { cheaperModel } from '../src/models'

export default evaluate({
  task: support,

  cases: [
    {
      id: 'refund',
      input: { question: 'Can I get a refund?' },
      expected: { answer: 'Yes' },
    },
  ],

  variants: {
    cheaper: { model: cheaperModel },
  },

  expect: ({ output, expected, expect }) => {
    expect(output.answer).toBe(expected.answer)
  },
})

03 · Just enough work

Change anything. Crux knows what to recompute.

Select a change to see the intended behavior. Green means new work; blue means trusted evidence reused.

V1 is deliberately conservative. Opaque functions, untracked external data, performance measurements, and toolful workflows with possible side effects rerun unless Crux can prove complete managed-task identity. Reusing stale evidence is a correctness bug; extra work is only slower.
Checks

Three ways to say what good means.

Beginners can start with assertions. Measurement and release policy appear only when the problem needs them.

Expect

A deterministic assertion over output or captured behavior. Familiar unit-test semantics.

expect(output.answer).toBe('Yes')

Scorer

A measurement: exact metric, heuristic, or model judge. It produces evidence rather than deciding the release alone.

scorers: [correctness, citations]

Gate

The pass/fail policy over assertions and scores. It turns measurements into an actionable release decision.

gates: { correctness: { min: .9 } }
Blocking rule: a normal crux eval run is blocked by current-task gates; candidate variants are informational. Explicitly selecting --variant cheaper makes that candidate’s gates blocking. Adding an experiment therefore cannot unexpectedly break CI, while deliberate candidate validation remains strict.
04 · Optional branches

Recordings and Review solve different problems.

Neither belongs in the ordinary “write an eval and rerun it” workflow.

advanced · explicit

Recording: a future portable fixture

A deliberately updated, committed fixture for reproducing an eval elsewhere. It is not the automatic result cache, and it should not ship until its strict promise is true across every supported boundary.

  1. V1 --offline uses only exact reusable results and makes zero external calls.
  2. A missing result is listed precisely and the run stops.
  3. A later recordings RFC adds explicit portable fixtures without changing the ordinary workflow.
production bridge · optional

Review: turn real problems into cases

Feedback attaches to the existing production run. Standard message integrations carry that link automatically.

  1. A user rates a production message.
  2. Crux creates a Review item linked to its run.
  3. A human dismisses, resolves, or adds it to an eval.
authenticated servermessage already carries its run
import { feedback } from '@use-crux/ai/feedback'

const message = await messages.getOwned(messageId, user.id)

await feedback(message, {
  rating: 'down',
  comment: 'It used the old refund policy.',
  correction: { answer: 'Refunds are available within 30 days.' },
})

// Creates a Review item. Never changes an eval or baseline automatically.
The destination is explicit infrastructure, not a second runtime. feedback() writes through the application’s configured Crux observability destination, which durably stores the Review record and its run link. Devtools reads that same destination. If no durable destination is configured, submission fails with the exact setup action instead of pretending it worked.
05 · Where it runs

One runtime concept, honest execution.

The CLI and Devtools coordinate evals. The task executes where the application can truthfully execute it.

CLI coordinator

Discovers evals, plans work, enforces budget, assembles evidence, and reports progress. A later Devtools trigger invokes this same contract.

coordinates →

The task’s real host

Local Node when portable; Worker, serverless function, or Convex when host-bound.

There is no public “Quality runtime.” Crux uses the application’s existing runtime and host capabilities.
What Crux stores underneath—without making users manage it
  • Project truth: eval source, accepted cases, and promoted baseline snapshots live in Git.
  • Private reusable evidence: exact task/judge outputs, fingerprints, and freshness are automatic and gitignored locally; a configured shared store can carry them across CI machines.
  • Remote execution state: an accepted host job, its idempotency state, normalized result, and failure/cancellation are durably stored by the real host before completion is reported.
  • Production Review evidence: feedback records and their run links travel through the configured at-least-once observability destination into durable storage; Devtools reads the same records.
How a host-bound task stays honest
The deployed host owns a generated registry of allowed tasks and variants. Before inference, coordinator and host compare fingerprints. Missing or stale deployment fails before spend with the exact generate/deploy action. No functions, routers, or closures are serialized over the wire, and observability is evidence rather than the control plane.

Optional programmatic execution

Definitions remain inert and edge-safe. A separate Node coordinator API exists for scripts and test harnesses; it is never required by the CLI. Add id: 'support' to the definition when opting into direct execution, then:

programmatic.tssame semantics as the CLI
import supportEval from './evals/support.eval'
import { runEval } from '@use-crux/core/eval/node'

const result = await runEval(supportEval, {
  maxCostUsd: 5,
})

result.passed // EvalRun — never Experiment

Direct execution requires a definition-level id. CLI discovery still derives it automatically. Adding the same explicit ID changes nothing; a different ID is treated as a rename and migrated or explained, never silently forked. There is no anonymous ephemeral mode and no run-time identity override.

07 · Diagnosis

Crux has good ingredients, but the current product model is not stable enough.

The answer is neither “throw it all away” nor “polish the docs.” The internal boundaries and public vocabulary need deliberate change.

Current Crux

  • Vitest-like evaluate(), typed cases, assertions, scorers, and gates are strong foundations.
  • Evaluation, Experiment, Suite, Quality, and eval overlap publicly.
  • A source baseline variant conflicts with a promoted historical baseline.
  • Cassettes are public despite not reliably covering every execution boundary.
  • Execution and persistence assume Node in places that cannot honestly serve edge and host-bound tasks.
  • Reuse exists, but is surfaced as modes and mechanics rather than a trustworthy minimal-work planner.

Target Crux

  • One public vocabulary: Eval, Case, Variant, Eval run, Baseline.
  • The current task is always implicit; variants specify only differences.
  • Automatic private reuse is default and explained per result.
  • Portable recordings are explicit and ship only when strict across supported boundaries.
  • CLI/Devtools coordinate; the task runs in its real host through the existing runtime.
  • Production feedback creates Review items that humans can turn into source-controlled cases.
Verdict: preserve the typed authoring, evidence, scoring, gates, and observability foundations. Fundamentally revise the public model, baseline semantics, replay promise, incremental planner, and host execution boundary before launch.
Code-audit anchors behind this verdict
  • packages/core/src/quality/evaluate.ts contains the strong typed evaluate() foundation, but publicly returns an Evaluation whose run result is an Experiment.
  • packages/core/src/quality/internal/engine.ts drops the unchanged task when authored variants exist and prevents promoted-baseline lookup when a source baseline is configured.
  • packages/core/src/quality/internal/output-cache.ts has useful exact cell-output identity, but normal CLI runs do not yet use automatic minimum-correct-work reuse.
  • packages/core/src/adapter/interception.ts explicitly excludes streaming interception; current cassettes also collapse identical stochastic occurrences.
  • packages/core/src/quality/internal/engine.ts, cassette context, cache, baseline, persistence, and feedback directly depend on Node APIs.
  • packages/core/src/quality/internal/feedback.ts is local/internal, accepts expected truth directly, and has no production run-aware API or Add-to-eval workflow.
  • The existing Runtime Engine has real host binding for serverless and Convex, but Quality has no remote eval-job/result protocol and no first-party Cloudflare host adapter yet.
08 · Honest failures

When magic cannot work, explain the exact fix.

“Just works” includes refusing unsafe or impossible work before spending money.

A host-bound eval was started without a ready host
Fail before inference: “research requires its deployed Convex host, but the registered fingerprint is missing or stale. Run the project-specific deploy command shown below, then rerun crux eval research.” Never simulate or silently fall back.
An unattended run would create new billable work
Show the planned new work and require an explicit --max-cost ceiling in US dollars. Reused zero-spend work needs no budget. An exhausted or incomplete run cannot pass or become a baseline.
An offline run lacks exact reusable evidence
List every missing case, variant, or required judge result and stop. Never make an external call under --offline. Portable committed recordings are a later RFC, not a hidden V1 fallback.
A scorer changed after the baseline was set
Keep compatible measurements, mark only the changed score incomparable, and explain it. A gate requiring that relative score makes the run incomplete rather than silently green.
09 · Scope

Small coherent release, deeper optimization later.

V1 must keep every correctness promise it exposes. More granular optimization can follow without changing the mental model.

Coherent V1

  • generate.task / stream.task and fully type-inferred eval cases and variants.
  • evaluate() from the single provider-neutral @use-crux/core/eval surface; provider packages only supply executable task helpers.
  • crux eval discovery, selectors, watch, plan, fresh, offline, and spend admission.
  • Optional runEval() from @use-crux/core/eval/node, using the same coordinator and requiring stable identity.
  • Current + variants, granular output/scorer/gate reuse, and explicit promoted baselines.
  • Portable coordinator/host protocol for Node, ordinary serverless, and Convex; reliable Workers support requires an explicit new first-party host adapter and conformance suite.
  • Eval catalog, run evidence, baseline setting, and Review workflow in Devtools.
  • Production feedback linked through run-aware message integrations and the configured durable observability destination.

RFC / later optimization

  • Partial recomputation inside an opaque multi-step task when only one nested prompt or tool changes.
  • Advanced statistical sequential testing and adaptive repeated sampling.
  • Shared/team evidence services and remote scheduling beyond the narrow host handshake.
  • Training-data and post-training exports—only after consent, provenance, review, and held-out certification are real.
  • Portable recordings become public only when streams, tools, media, repeated samples, judges, and every supported host obey the same strict contract.
Users write tests. Crux manages evidence.

That is the product boundary every API, CLI command, Devtools screen, cache key, and runtime decision should reinforce.
